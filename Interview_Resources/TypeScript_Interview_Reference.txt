====================================================
TOPIC 01 - WHAT IS TYPESCRIPT
====================================================

Question 1
What is TypeScript, and why would a team choose it over plain JavaScript?

Answer
TypeScript is a superset of JavaScript that adds static typing on top of it. Everything valid in JavaScript is valid in TypeScript, but TypeScript lets you describe the shape of your data before the code ever runs. The compiler checks those shapes and flags mismatches at compile time instead of letting them blow up in production. Teams pick it up mainly for two reasons: it catches a huge class of bugs early, and it makes large codebases easier to navigate because your editor can tell you exactly what a function expects and returns. I would not reach for it on a tiny throwaway script, but on anything that will be maintained by more than one person for more than a few weeks, the upfront cost of adding types pays for itself very quickly.

Example
function calculateTotal(price: number, quantity: number): number {
  return price * quantity;
}

calculateTotal(10, "5"); // compile-time error: Argument of type 'string' is not assignable to type 'number'

Follow-up Questions
Does TypeScript run directly in the browser or Node?
What happens to the types after compilation?
Is TypeScript a language or a tool?
How does TypeScript relate to ECMAScript proposals?

Common Mistakes
❌ Saying TypeScript is a completely different language from JavaScript.
❌ Believing TypeScript improves runtime performance.
❌ Thinking type errors are caught while the app is running in production.

Interview Tips
Interview Tip:
Make it clear that TypeScript is a compile-time tool only, it produces plain JavaScript and has zero runtime overhead of its own. Interviewers want to hear that you understand types disappear after compilation.

----------------------------------------------------

Question 2
How does TypeScript actually work under the hood? Walk me through the compilation process.

Answer
TypeScript code is written in .ts files, and the TypeScript compiler, tsc, parses that code into an abstract syntax tree, runs type checking against that tree, and then strips out all the type annotations to emit plain JavaScript. That JavaScript is what actually executes, whether in the browser or in Node. The type checking step is where all the value comes from; if there is a type error, tsc will report it, but by default it still emits the JavaScript output unless you have "noEmitOnError" turned on. In modern setups, tools like esbuild, swc, or Babel are often used to do the actual transpilation for speed, while tsc is run separately just for type checking.

Example
// input.ts
const greet = (name: string): string => `Hello, ${name}`;

// output.js (after compilation, types stripped)
const greet = (name) => `Hello, ${name}`;

Follow-up Questions
What does noEmitOnError do?
Why do some build pipelines separate type-checking from transpilation?
What is the difference between tsc and ts-node?

Common Mistakes
❌ Assuming a type error always stops the JavaScript from being generated.
❌ Confusing transpilation speed tools like esbuild with type checkers.

Interview Tips
Interview Tip:
Mention that type checking and code emission are two separate concerns in TypeScript's design. This distinction comes up a lot in build tooling discussions.

----------------------------------------------------

Question 3
What are the main benefits of using TypeScript in a production codebase?

Answer
The biggest benefit is catching bugs before they reach users, things like passing the wrong argument type, misspelling a property name, or forgetting to handle a null case. Beyond that, TypeScript makes refactoring far safer. If I rename a function or change its signature, the compiler tells me every single place that breaks, instead of me hoping I found them all by searching. It also massively improves the developer experience through autocomplete, inline documentation, and "go to definition" in the editor, since the tooling understands your types. On a team, it acts as a form of living documentation, because the types themselves describe what a function accepts and returns without needing separate docs that go stale.

Example
interface User {
  id: string;
  email: string;
  isActive: boolean;
}

function deactivateUser(user: User): User {
  return { ...user, isActive: false };
}
// Editor autocompletes user.id, user.email, user.isActive automatically

Follow-up Questions
How does TypeScript help with large-scale refactoring specifically?
Does TypeScript replace the need for unit tests?
How does TypeScript improve onboarding for new developers?

Common Mistakes
❌ Claiming TypeScript eliminates the need for testing entirely.
❌ Overselling TypeScript as catching all possible bugs, including logic errors.

Interview Tips
Interview Tip:
Be careful not to oversell it. A good answer acknowledges that TypeScript catches type-related bugs, not logic bugs or runtime issues like network failures. Interviewers respect that nuance.

----------------------------------------------------

Question 4
What are some downsides or trade-offs of using TypeScript?

Answer
TypeScript adds a build step and some initial learning curve, especially around generics and advanced utility types. On small projects or quick prototypes, writing types can feel like overhead that slows you down for little benefit. Type definitions for third-party libraries are not always accurate or available, which sometimes means writing your own ambient declarations or falling back to any. There is also a real risk of teams over-engineering their types, spending more time satisfying the compiler than shipping features. I have seen codebases where deeply nested generic types became harder to read than the JavaScript they were replacing.

Example
// Overly complex type that hurts readability
type DeepPartial<T> = T extends object
  ? { [P in keyof T]?: DeepPartial<T[P]> }
  : T;

Follow-up Questions
When would you NOT recommend using TypeScript?
How do you avoid "type gymnastics" in a codebase?
How do you handle third-party libraries without good type definitions?

Common Mistakes
❌ Pretending TypeScript has no downsides at all.
❌ Not being able to name a real trade-off when asked directly.

Interview Tips
Interview Tip:
Interviewers specifically ask this to see if you can think critically instead of reciting marketing points. Always have at least one genuine downside ready.

----------------------------------------------------

Question 5
Is TypeScript a compiled language or an interpreted language?

Answer
Neither in the traditional sense. TypeScript is transpiled, meaning it is converted from one high-level language into another high-level language, JavaScript, rather than compiled down to machine code or bytecode. Once transpiled, the resulting JavaScript is then either interpreted or JIT-compiled by the JavaScript engine, like V8. So TypeScript itself never runs; it exists purely at development and build time to give you type safety, and by the time your code is running, TypeScript is completely gone.

Example
// tsc converts this TypeScript
let age: number = 30;

// into this JavaScript, which is what actually runs
let age = 30;

Follow-up Questions
What is the difference between transpiling and compiling?
Does the TypeScript compiler do any optimization?
What JavaScript engines run the final output?

Common Mistakes
❌ Calling TypeScript a compiled language in the same sense as C++ or Java.
❌ Thinking the browser can run .ts files directly.

Interview Tips
Interview Tip:
Using the word "transpile" instead of "compile" shows precision and is a small detail that senior interviewers notice.



====================================================
TOPIC 02 - INFERENCE
====================================================

Question 1
What is type inference in TypeScript?

Answer
Type inference is TypeScript's ability to figure out the type of a variable, parameter, or return value automatically, without you writing an explicit annotation. When I write const count = 5, TypeScript looks at the value on the right-hand side and infers that count is of type number, without me needing to write const count: number = 5. This makes code much less verbose while still keeping full type safety. Inference also works across function boundaries, contextual typing in callbacks, and return statements. I rely on inference constantly and only add explicit annotations when the inferred type would be wrong, too broad, or when I am defining a public API where I want the contract to be explicit and readable.

Example
function add(a: number, b: number) {
  return a + b; // return type inferred as number
}

const result = add(2, 3); // result inferred as number

Follow-up Questions
When should you rely on inference versus writing explicit types?
Does inference work for function parameters?
What is contextual typing?

Common Mistakes
❌ Believing TypeScript can infer parameter types without any context.
❌ Over-annotating variables where inference already gives the correct, narrow type.

Interview Tips
Interview Tip:
A strong answer mentions that annotating everything explicitly is actually considered bad practice in idiomatic TypeScript; let the compiler do the work where it can.

----------------------------------------------------

Question 2
Why can't TypeScript infer the types of function parameters the way it infers variable types?

Answer
Variables have an initializer, an actual value assigned right there, so TypeScript can look at that value and infer its type immediately. Function parameters, on the other hand, do not have a value until the function is actually called, so there is nothing for the compiler to look at in isolation. The exception is contextual typing, where TypeScript infers a parameter's type based on the context it is used in, such as a callback being passed to a typed function like array.map. Outside of that contextual scenario, parameters default to the "any" type if you have implicit any enabled, or throw a compiler error if "noImplicitAny" is turned on, which is why almost every production tsconfig enables that flag.

Example
const numbers = [1, 2, 3];
numbers.map((n) => n * 2); // 'n' is contextually inferred as number, no annotation needed

function multiply(a, b) { // error under noImplicitAny: 'a' and 'b' implicitly have an 'any' type
  return a * b;
}

Follow-up Questions
What does noImplicitAny actually enforce?
How does contextual typing work with array methods like map and filter?
Why is implicit any considered dangerous?

Common Mistakes
❌ Forgetting that noImplicitAny is what forces explicit parameter types.
❌ Thinking contextual typing works everywhere, even outside typed callback positions.

Interview Tips
Interview Tip:
Bring up noImplicitAny by name. It is one of the most commonly discussed tsconfig flags in interviews and shows you understand real project configuration, not just syntax.

----------------------------------------------------

Question 3
What is the "best common type" algorithm, and how does it relate to inference in arrays?

Answer
When TypeScript infers the type of an array literal with mixed but related values, it looks at all the elements and tries to find a type that all of them are compatible with. This is called the best common type algorithm. For example, an array containing a number and a string infers as (number | string)[], because that is the most specific union that covers every element. If the elements share a common supertype, like several classes extending a base class, TypeScript will infer the array as that base type instead of a giant union, if it can. When no single reasonable common type exists, it may fall back to a wider type or, in rare cases, any[] with a warning under strict settings.

Example
const mixed = [1, "two", 3]; // inferred as (string | number)[]

class Cat {}
class Dog {}
const animals = [new Cat(), new Dog()]; // inferred as (Cat | Dog)[]

Follow-up Questions
How can you force a narrower or wider type for an array literal?
What happens when array elements have no relationship at all?
How does this interact with const assertions?

Common Mistakes
❌ Expecting the inferred type to always be a broad type like any[].
❌ Not realizing the inferred union can grow unexpectedly with heterogeneous data.

Interview Tips
Interview Tip:
Mention that explicit typing or "as const" is the usual fix when the inferred union becomes too wide for what you actually want to allow.


====================================================
TOPIC 03 - PRIMITIVES
====================================================

Question 1
What are the primitive types in TypeScript?

Answer
TypeScript's primitives mirror JavaScript's: string, number, boolean, null, undefined, symbol, and bigint. Each represents a single, immutable value rather than an object with properties. TypeScript enforces that you use them correctly, so a variable typed as string cannot later be assigned a number. One thing that trips people up is that TypeScript also has capitalized wrapper types, String, Number, Boolean, which represent the boxed object versions from JavaScript, and using those in type annotations instead of the lowercase primitives is considered a mistake because it accepts a much wider and less safe set of values.

Example
let username: string = "afnan";
let age: number = 28;
let isVerified: boolean = true;
let id: symbol = Symbol("unique");
let bigNumber: bigint = 9007199254740993n;

Follow-up Questions
What's the difference between string and String as a type?
Why does TypeScript discourage the boxed wrapper types?
When would you actually use bigint over number?

Common Mistakes
❌ Using capitalized String, Number, or Boolean as type annotations.
❌ Forgetting that null and undefined are also primitive types.

Interview Tips
Interview Tip:
If asked to write a type annotation, always default to lowercase primitives. Reaching for String or Number is an instant red flag in a code review setting.

----------------------------------------------------

Question 2
What is the difference between null and undefined in TypeScript, and how does strictNullChecks affect them?

Answer
undefined typically means a variable has been declared but not yet assigned a value, while null is an explicit, intentional absence of a value that a developer assigns deliberately. Without strictNullChecks enabled, TypeScript treats null and undefined as assignable to every type, which basically defeats a huge part of the safety TypeScript is supposed to give you. Once strictNullChecks is turned on, null and undefined become their own distinct types, and you have to explicitly include them in a union, like string | null, if you want a variable to allow them. This forces you to handle the null or undefined case before using the value, which eliminates a massive category of runtime errors.

Example
function getUser(id: string): string | null {
  return id === "404" ? null : "Afnan Khan";
}

const user = getUser("1");
console.log(user.toUpperCase()); // error under strictNullChecks: user might be null
if (user) {
  console.log(user.toUpperCase()); // safe after the null check
}

Follow-up Questions
Why is strictNullChecks considered one of the most important compiler flags?
What is the non-null assertion operator and when is it risky?
How do optional chaining and nullish coalescing help here?

Common Mistakes
❌ Running a project without strictNullChecks and assuming it is safe by default.
❌ Overusing the non-null assertion operator (!) to silence errors instead of handling them.

Interview Tips
Interview Tip:
Say clearly that strictNullChecks should be non-negotiable on any real project. Interviewers use this question to check if you've actually configured a tsconfig yourself.

----------------------------------------------------

Question 3
What is the void type and how is it different from undefined?

Answer
void represents the absence of a meaningful return value, and it is used almost exclusively as a return type for functions that do not return anything useful, like a function that only logs something or fires a side effect. undefined, on the other hand, is an actual value that a variable can hold. The subtle but important difference is that a function typed to return void can technically still return a value in JavaScript at runtime, and TypeScript will often not complain, because void just tells the caller "don't rely on the return value," rather than "there is definitely no return value." This is especially relevant with callback types, where a void return type allows the caller to pass functions that return other things without a mismatch.

Example
function logMessage(message: string): void {
  console.log(message);
}

// void is permissive for callbacks
const items = [1, 2, 3];
items.forEach((item): void => {
  console.log(item); // forEach's callback expects void, but console.log itself returns undefined, which is fine
});

Follow-up Questions
Can a void-typed function actually return a value at runtime?
Why does void behave differently in callback positions compared to variable positions?
When would you use undefined as a return type instead of void?

Common Mistakes
❌ Treating void and undefined as fully interchangeable in every context.
❌ Being surprised that array callback types often use void deliberately.

Interview Tips
Interview Tip:
This is a favorite "gotcha" question at mid-to-senior level. Explaining the callback contravariance behavior of void shows real depth.



====================================================
TOPIC 04 - SPECIAL TYPES
====================================================

Question 1
What is the "any" type, and why is it considered dangerous?

Answer
any is TypeScript's escape hatch. When a variable is typed as any, the compiler completely turns off type checking for it, meaning you can assign anything to it, call any method on it, and pass it anywhere, with zero safety net. It essentially opts that piece of code out of TypeScript entirely. The danger is that any is contagious: once a value of type any flows into other parts of the code, it can silently erase type safety wherever it touches, because TypeScript won't flag operations on it. I treat any as a last resort, usually only acceptable temporarily while migrating a JavaScript codebase, or in very narrow, well-documented spots, never as a default choice.

Example
let data: any = fetchData();
data.someProperty.deeplyNested.value; // no error, even if this doesn't exist, and it will crash at runtime

Follow-up Questions
How is any different from unknown?
What does noImplicitAny actually protect against?
How does any spread through a codebase?

Common Mistakes
❌ Using any to silence a compiler error instead of fixing the underlying type issue.
❌ Not realizing any disables checking for everything that value touches downstream.

Interview Tips
Interview Tip:
Say explicitly that unknown should almost always be preferred over any in modern TypeScript. This single sentence signals real experience.

----------------------------------------------------

Question 2
What is the "never" type, and where does it actually show up in real code?

Answer
never represents a value that can never occur, it's the type of a function that never successfully returns, either because it always throws, or because it has an infinite loop. It also shows up as the result of narrowing a union down to nothing, which is extremely useful for writing exhaustive switch statements, because if you add a new case to a union later and forget to handle it in the switch, TypeScript will flag the unhandled case at the default branch, since it expected the type there to be never. I use never mainly in two places: functions that always throw, like an assertion helper, and exhaustiveness checks in discriminated union handling.

Example
function throwError(message: string): never {
  throw new Error(message);
}

type Shape = { kind: "circle"; radius: number } | { kind: "square"; side: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.side ** 2;
    default:
      const exhaustiveCheck: never = shape; // error here if a new shape variant is added and not handled
      return exhaustiveCheck;
  }
}

Follow-up Questions
How is never different from void?
How does never help with exhaustive checking in switch statements?
Can you assign anything to a variable of type never?

Common Mistakes
❌ Confusing never with void, thinking they both just mean "no return value."
❌ Not using never for exhaustiveness checks, missing a great safety pattern.

Interview Tips
Interview Tip:
The exhaustiveness-check pattern with never is a strong senior-level answer. Bring it up unprompted if the topic of discriminated unions comes up anywhere else in the interview.

----------------------------------------------------

Question 3
What does the "unknown" type mean, and how do you actually use a value typed as unknown?

Answer
unknown is the type-safe counterpart to any. It can hold any value, just like any, but the key difference is that TypeScript will not let you do anything with it until you narrow it down to a more specific type first, through something like typeof, instanceof, or a custom type guard. This forces you to actually check what you have before operating on it, which is exactly the kind of safety any throws away. I reach for unknown any time I'm dealing with data whose shape I don't control yet, like the response from an API call or user input, before validating it.

Example
function processInput(input: unknown) {
  if (typeof input === "string") {
    console.log(input.toUpperCase()); // safe, narrowed to string
  } else if (Array.isArray(input)) {
    console.log(input.length); // safe, narrowed to array
  }
}

Follow-up Questions
Why is unknown safer than any?
What happens if you try to call a method directly on an unknown value?
How does unknown pair with type guards or libraries like Zod?

Common Mistakes
❌ Using any as a synonym for "I don't know the type yet," when unknown is almost always the correct choice.
❌ Trying to access properties on an unknown value without narrowing first.

Interview Tips
Interview Tip:
Mention that unknown forces runtime validation before use. Interviewers really like hearing that specific phrase because it shows you understand the design intent, not just the syntax.


====================================================
TOPIC 05 - OBJECTS
====================================================

Question 1
How do you type an object in TypeScript, and what happens if you pass extra properties?

Answer
You can type an object either inline with an object type literal or by defining a separate interface or type alias, which is what I do for anything reused more than once. TypeScript checks object types structurally, meaning it cares about the shape, not the name. One important behavior is "excess property checking," which only applies when you pass an object literal directly to a typed parameter or variable. In that case, TypeScript will flag any extra properties that aren't part of the declared type. If you instead assign the object to a variable first and then pass that variable, excess property checking doesn't apply, because at that point it's just checking structural compatibility, not literal shape.

Example
interface Point {
  x: number;
  y: number;
}

function printPoint(point: Point) {
  console.log(point.x, point.y);
}

printPoint({ x: 1, y: 2, z: 3 }); // error: object literal has excess property 'z'

const p = { x: 1, y: 2, z: 3 };
printPoint(p); // no error, structural typing allows extra properties on a variable

Follow-up Questions
Why does excess property checking only apply to object literals?
What is structural typing and how is it different from nominal typing?
How do optional properties affect object type checks?

Common Mistakes
❌ Being confused about why the same "extra property" fails in one case and not another.
❌ Assuming TypeScript enforces exact object shapes everywhere.

Interview Tips
Interview Tip:
This literal-versus-variable distinction is a classic trick question. Walking through both examples out loud shows a genuinely deep understanding of TypeScript's type system.

----------------------------------------------------

Question 2
What is structural typing, and how does it differ from the nominal typing used in languages like Java or C#?

Answer
TypeScript uses structural typing, sometimes called "duck typing," which means type compatibility is based entirely on the shape of the data, what properties and methods exist, rather than the explicit name of the type. Two completely unrelated interfaces are considered compatible if they happen to have the same members. This is very different from nominal typing in languages like Java, where a class must explicitly implement an interface by name to be considered compatible, even if the shapes match exactly. Structural typing gives TypeScript a lot of flexibility, especially for things like mocking objects in tests or working with plain data, but it also means two types that look similar by accident can be assigned to each other even if that wasn't intended.

Example
interface Bird { fly(): void; layEggs(): void; }
interface Airplane { fly(): void; layEggs(): void; }

let bird: Bird = { fly: () => {}, layEggs: () => {} };
let airplane: Airplane = bird; // valid, structurally compatible even though unrelated by name

Follow-up Questions
What are the practical benefits of structural typing?
What are the risks or surprises that come from structural typing?
How would you simulate nominal typing in TypeScript if you needed it?

Common Mistakes
❌ Assuming TypeScript checks the declared type name instead of the actual shape.
❌ Not knowing how to explain "duck typing" when asked directly.

Interview Tips
Interview Tip:
Mention "if it looks like a duck and quacks like a duck" as a memorable way to explain structural typing, then immediately follow with the formal term so it sounds professional, not just casual.

----------------------------------------------------

Question 3
How do you make object properties optional or readonly, and what's the difference between the two?

Answer
You mark a property optional with a question mark after its name, which means the property can be omitted entirely or explicitly set to undefined. You mark a property readonly by prefixing it with the readonly keyword, which means it can be set once during object creation but not reassigned afterward. These solve two completely different problems: optional is about whether a property must be present, while readonly is about whether a property, once present, can change. They can also be combined on the same property. It's worth noting readonly is a compile-time-only constraint; it doesn't freeze the object at runtime the way Object.freeze does.

Example
interface UserProfile {
  readonly id: string;
  displayName?: string;
}

const profile: UserProfile = { id: "abc123" };
profile.displayName = "Afnan"; // fine, optional property being set
profile.id = "xyz789"; // error: cannot assign to 'id' because it is a read-only property

Follow-up Questions
Does readonly provide any runtime protection, or is it compile-time only?
How does optional differ from a property typed as string | undefined?
What is the Readonly<T> utility type and how does it relate to this?

Common Mistakes
❌ Believing readonly prevents mutation at runtime the same way Object.freeze does.
❌ Treating an optional property the same as one explicitly typed with | undefined, they behave slightly differently with exactOptionalPropertyTypes.

Interview Tips
Interview Tip:
If you know about exactOptionalPropertyTypes, mention it briefly, it is an advanced flag that shows you've dealt with subtle real-world edge cases around optional properties.


====================================================
TOPIC 06 - LITERALS
====================================================

Question 1
What are literal types in TypeScript?

Answer
A literal type narrows a general type like string or number down to one exact, specific value. Instead of a variable being typed as any string, it can be typed as exactly "success", meaning only that precise value is valid. Literal types are the foundation of a lot of powerful TypeScript patterns, especially discriminated unions, where a "kind" or "type" field is a union of specific string literals used to distinguish between different object shapes. They're commonly combined with union types to represent a fixed, closed set of allowed values, which is a much safer alternative to a plain string when you know exactly what values are valid.

Example
let status: "pending" | "success" | "error";
status = "success"; // valid
status = "loading"; // error: not assignable to type '"pending" | "success" | "error"'

Follow-up Questions
How do literal types improve on using enums or plain strings?
What is a discriminated union and how do literal types enable it?
Why does TypeScript widen a literal type by default when using let?

Common Mistakes
❌ Using a plain string type when a union of literals would be far safer and more descriptive.
❌ Not understanding why let widens a literal while const preserves it.

Interview Tips
Interview Tip:
Bring up discriminated unions here even if not asked directly. It shows you understand literal types aren't just a syntax trick, they enable a whole design pattern.

----------------------------------------------------

Question 2
Why does declaring a variable with let widen a literal type, while const preserves it?

Answer
When you declare a variable with let, TypeScript assumes the value might be reassigned later, so instead of inferring the narrowest possible literal type, it widens the inference to the general type, like string or number, to allow future reassignment to any value of that broader type. With const, TypeScript knows the value can never change after initialization, so it's safe to infer the exact literal type, since there's no risk of a wider value being assigned later. This widening behavior is a common source of confusion when passing let-declared variables into functions expecting a specific literal type.

Example
let direction = "left";    // inferred as string, not "left"
const fixedDirection = "left"; // inferred as literal type "left"

function move(dir: "left" | "right") { /* ... */ }
move(direction);      // error: 'string' is not assignable to '"left" | "right"'
move(fixedDirection); // valid

Follow-up Questions
How would you fix the error in the let example without changing let to const?
What is the "as const" assertion and how does it relate to widening?
Does this widening behavior apply to object properties too?

Common Mistakes
❌ Not realizing this is why a seemingly correct string value fails to match a literal union type.
❌ Forgetting that object literal properties widen by default even inside a const-declared object.

Interview Tips
Interview Tip:
If you can explain widening clearly and mention "as const" as the fix, that alone often separates mid-level candidates from senior ones on this exact question.

----------------------------------------------------

Question 3
Can you have literal types for numbers and booleans too, or is this exclusive to strings?

Answer
Literal types work for numbers and booleans just as well as strings. A numeric literal type restricts a value to one exact number, like 200 or 404, which is genuinely useful for things like HTTP status codes or fixed configuration flags. Boolean literal types restrict a value to exactly true or exactly false, which shows up often in function overloads or conditional types where the boolean value itself changes the shape of the return type. All three, string, number, and boolean literals, follow the same rules around widening and combine naturally with union types.

Example
type SuccessCode = 200 | 201 | 204;
type ErrorCode = 400 | 404 | 500;

function handleResponse(code: SuccessCode | ErrorCode) { /* ... */ }

function toggle(flag: true): "on";
function toggle(flag: false): "off";
function toggle(flag: boolean): string {
  return flag ? "on" : "off";
}

Follow-up Questions
Where have you seen numeric literal types used in a real codebase?
How do boolean literal types interact with function overloads?
Can literal types be combined with template literal types?

Common Mistakes
❌ Assuming literal types are a string-only feature.
❌ Not recognizing numeric literal unions as a cleaner alternative to loosely typed magic numbers.

Interview Tips
Interview Tip:
Giving the HTTP status code example is a very relatable, real-world way to demonstrate numeric literals without sounding like you memorized documentation.



====================================================
TOPIC 07 - ASSERTIONS
====================================================

Question 1
What is a type assertion, and how is it different from type casting in other languages?

Answer
A type assertion tells the TypeScript compiler "trust me, I know this value is actually this type," using the as keyword, or the angle-bracket syntax in non-JSX files. It's important to understand this does not perform any actual conversion at runtime the way casting does in languages like C# or Java; it purely affects how the compiler treats the value during type checking. Because of that, a type assertion can lie to the compiler if used incorrectly, since TypeScript trusts your assertion rather than verifying it. I use assertions sparingly, mainly when I have information the compiler can't infer on its own, like knowing a DOM query will definitely return a specific element type.

Example
const input = document.getElementById("email") as HTMLInputElement;
console.log(input.value); // TypeScript now knows this is an input element

// This compiles but is a lie, and will fail at runtime
const fakeNumber = "hello" as unknown as number;

Follow-up Questions
Why is a type assertion not the same as runtime type conversion?
Why does TypeScript sometimes require a double assertion through unknown?
When is a type assertion actually the right tool versus a type guard?

Common Mistakes
❌ Believing "as SomeType" actually converts or validates the value at runtime.
❌ Overusing assertions to silence errors instead of properly narrowing or validating the value.

Interview Tips
Interview Tip:
Say clearly that assertions are a compile-time-only construct. This is the single most important fact interviewers are listening for on this topic.

----------------------------------------------------

Question 2
When would using a type assertion be considered dangerous or a bad practice?

Answer
A type assertion becomes dangerous whenever it's used to force a type onto a value that hasn't actually been verified to match, essentially telling the compiler to stop protecting you. The classic bad case is asserting the result of an API call directly to a specific interface without validating the response, because if the API returns something unexpected, the assertion silently allows the mismatch to slip past the compiler and blow up somewhere deep in the application logic instead. Assertions are appropriate when you genuinely have more information than the compiler, like knowing a specific DOM element exists on the page. They are inappropriate as a substitute for actual validation of untrusted data, like network responses or user input.

Example
interface ApiUser { id: string; name: string; }

async function getUser(): Promise<ApiUser> {
  const response = await fetch("/api/user");
  return response.json() as ApiUser; // dangerous: no runtime check that the shape actually matches
}

Follow-up Questions
What would you use instead of an assertion when handling API responses?
How does this connect to the unknown type and runtime validation libraries?
Have you seen a bug caused by an incorrect assertion in production?

Common Mistakes
❌ Treating "as ApiUser" as equivalent to validating the response actually matches ApiUser.
❌ Using assertions on external, untrusted data instead of internal, well-known data.

Interview Tips
Interview Tip:
Bringing up Zod or a similar runtime validation library here as the "correct" alternative to blind assertions is a strong, senior-sounding answer.

----------------------------------------------------

Question 3
What is the non-null assertion operator, and how is it different from a regular type assertion?

Answer
The non-null assertion operator is the exclamation mark placed after an expression, and it tells TypeScript to remove null and undefined from that expression's type, without actually checking whether the value is truly non-null at runtime. It's a much narrower tool than a full "as" assertion, since it only affects nullability, not the entire type. I use it very sparingly, typically only when I have certain external knowledge, like a value that was just checked a few lines above but the compiler lost track of the narrowing due to a closure or async boundary. Using it carelessly reintroduces exactly the kind of null-reference bugs that strictNullChecks was meant to prevent.

Example
function getElementText(id: string): string {
  const el = document.getElementById(id);
  return el!.textContent!; // asserting el is not null, and textContent is not null
}

Follow-up Questions
Why is the non-null assertion operator considered risky?
How is it different from optional chaining?
What's a safer alternative when you're unsure if a value could be null?

Common Mistakes
❌ Using ! as a default habit instead of properly narrowing with an if check.
❌ Confusing the non-null assertion operator (!) with the logical NOT operator.

Interview Tips
Interview Tip:
Mention that overusing the non-null assertion operator is often flagged in code review, and that it should come with a comment explaining why the value is guaranteed to exist.


====================================================
TOPIC 08 - AS CONST
====================================================

Question 1
What does the "as const" assertion do, and why is it useful?

Answer
"as const" tells TypeScript to infer the narrowest, most literal possible type for a value, instead of the wider, general type it would normally infer. For a primitive, that means inferring the exact literal value instead of its general type. For an array, it infers a readonly tuple with each position's exact literal type, instead of a general mutable array type. For an object, every property becomes readonly and every value becomes its literal type instead of being widened. I reach for "as const" constantly when defining fixed configuration objects, enums-as-objects, or arrays of allowed values that I want treated as an exact, immutable set rather than a general type.

Example
const colors = ["red", "green", "blue"] as const;
// type is readonly ["red", "green", "blue"], not string[]

const config = {
  env: "production",
  retries: 3,
} as const;
// env is type "production", not string; retries is type 3, not number

Follow-up Questions
How does "as const" interact with readonly arrays and tuples?
How is "as const" different from explicitly typing something as a union of literals?
Can you use "as const" to build a type-safe alternative to enums?

Common Mistakes
❌ Forgetting that "as const" makes arrays and object properties readonly, which can cause unexpected mutation errors.
❌ Not realizing "as const" is often the cleanest way to derive literal union types from a plain array.

Interview Tips
Interview Tip:
Show the pattern of deriving a union type from an "as const" array using typeof and [number]. It's one of the most useful and commonly asked "as const" tricks.

----------------------------------------------------

Question 2
How can you derive a union type from an array using "as const"?

Answer
This is one of the most practical "as const" patterns. If you define an array of allowed values and mark it "as const", TypeScript infers it as a readonly tuple of literal types. You can then use typeof on that array combined with indexing by [number] to extract a union type of every element in the array. This gives you a single source of truth: the runtime array of values and the compile-time union type stay perfectly in sync, so if you add a new value to the array, the type automatically updates too, without needing to maintain two separate lists.

Example
const roles = ["admin", "editor", "viewer"] as const;
type Role = typeof roles[number]; // "admin" | "editor" | "viewer"

function assignRole(role: Role) { /* ... */ }
assignRole("admin"); // valid
assignRole("guest"); // error: not assignable to type 'Role'

Follow-up Questions
Why is this pattern preferred over manually writing out the union type separately?
What would happen if you forgot the "as const" in this example?
How does this compare to using a TypeScript enum for the same purpose?

Common Mistakes
❌ Forgetting "as const", which causes typeof roles[number] to just be string, losing all the literal precision.
❌ Manually duplicating the union type in a separate type declaration instead of deriving it from the array.

Interview Tips
Interview Tip:
This exact pattern, array of values plus derived union type, is asked constantly in mid-to-senior interviews. Have it memorized and ready to type out from scratch.

----------------------------------------------------

Question 3
Does "as const" provide runtime immutability, or is it purely a compile-time construct?

Answer
"as const" is purely a compile-time construct, just like every other type assertion. It marks properties as readonly and infers literal types so the compiler will stop you from reassigning or widening the value, but it does not call Object.freeze or do anything at all to the actual JavaScript object at runtime. That means if you bypass the type system, for instance by using an "as any" cast or plain JavaScript code, you can still mutate a value that was marked "as const" at compile time. If you need real runtime immutability, you still need Object.freeze, and ideally both together for full protection.

Example
const point = { x: 1, y: 2 } as const;
point.x = 5; // compile-time error, blocked by the type system

const anyPoint = point as any;
anyPoint.x = 5; // no compiler error, and this actually mutates the object at runtime

Follow-up Questions
How would you achieve true runtime immutability alongside compile-time immutability?
Why does casting through "any" bypass "as const" protection?
Is there a performance cost to using Object.freeze at runtime?

Common Mistakes
❌ Assuming "as const" makes an object frozen or immutable in the running JavaScript.
❌ Not knowing that casting through any can bypass all compile-time protections, including as const.

Interview Tips
Interview Tip:
This question tests whether you truly understand that TypeScript's type system disappears at runtime. Always tie your answer back to that core principle.

TOPIC 09 - UNIONS
====================================================

Question 1
What is a union type, and how do you work with values that could be one of several types?

Answer
A union type describes a value that could be one of several possible types, written with a pipe symbol between each option. When working with a union-typed value, TypeScript only lets you access properties or methods that are common to every type in the union, because it can't know at that point which specific type you actually have. To access something specific to just one branch, you need to narrow the type first, usually with a typeof check, an instanceof check, or a custom type guard, after which TypeScript automatically restricts the value to just the matching branch within that code block.

Example
function formatId(id: string | number): string {
  if (typeof id === "string") {
    return id.toUpperCase(); // narrowed to string here
  }
  return id.toFixed(2); // narrowed to number here
}

Follow-up Questions
Why can't you access type-specific properties on a union without narrowing first?
What narrowing techniques are available besides typeof?
How is a union type different from an intersection type?

Common Mistakes
❌ Trying to call a method that only exists on one branch of the union without narrowing first.
❌ Confusing the pipe symbol for unions with the ampersand used for intersections.

Interview Tips
Interview Tip:
Whenever you explain a union, immediately follow with a narrowing example. Interviewers want to see that you understand unions and narrowing as one connected concept, not two separate topics.

----------------------------------------------------

Question 2
What is a discriminated union, and why is it considered one of TypeScript's most powerful patterns?

Answer
A discriminated union is a union of object types that all share a common property, usually called a "kind" or "type," where each member has a different literal value for that property. That shared literal property acts as a tag the compiler can use to automatically narrow the whole object down to the exact matching type once you check its value, typically inside a switch statement or an if check. This pattern is powerful because it makes illegal states genuinely unrepresentable, you can't accidentally access a property that doesn't belong to the current variant, and combined with a never-typed exhaustiveness check, it guarantees every case is handled.

Example
type LoadingState = { status: "loading" };
type SuccessState = { status: "success"; data: string[] };
type ErrorState = { status: "error"; message: string };
type RequestState = LoadingState | SuccessState | ErrorState;

function render(state: RequestState) {
  switch (state.status) {
    case "loading": return "Loading...";
    case "success": return state.data.join(", "); // narrowed, data is accessible
    case "error": return state.message; // narrowed, message is accessible
  }
}

Follow-up Questions
Why is a discriminated union safer than a single object with lots of optional properties?
How does exhaustiveness checking with never reinforce this pattern?
Where have you used discriminated unions in a real project, like handling async states?

Common Mistakes
❌ Modeling state with many optional properties instead of a proper discriminated union.
❌ Forgetting to add an exhaustiveness check, which silently allows unhandled cases to slip through.

Interview Tips
Interview Tip:
Use the exact phrase "make illegal states unrepresentable." It's a well-known concept in the TypeScript community and instantly signals strong design thinking.

----------------------------------------------------

Question 3
How does TypeScript narrow a union type inside conditional blocks, and what techniques can you use?

Answer
TypeScript performs what's called control flow analysis, tracking the possible type of a variable as it flows through your code based on the checks you perform. The main narrowing techniques are typeof for primitives, instanceof for class instances, the "in" operator for checking whether a property exists on an object, direct equality checks against literal values for discriminated unions, and custom type predicate functions for more complex logic. Each of these, when used inside an if, switch, or early return, causes TypeScript to automatically narrow the type of the variable within that specific branch, without you needing any extra casting.

Example
function describe(value: string | string[] | Date) {
  if (typeof value === "string") return value.trim();
  if (Array.isArray(value)) return value.join(", ");
  return value.toISOString(); // narrowed to Date by elimination
}

Follow-up Questions
What is the "in" operator narrowing technique used for?
How do custom type predicates extend narrowing beyond built-in checks?
Does narrowing work across function calls, or only within a single scope?

Common Mistakes
❌ Assuming narrowing persists after calling an external function that could theoretically mutate the variable.
❌ Not knowing Array.isArray is itself a narrowing check for arrays within a union.

Interview Tips
Interview Tip:
Mention "control flow analysis" by name. It's the formal term for what's happening under the hood and it shows you understand the mechanism, not just the outcome.

TOPIC 10 - INTERSECTIONS
====================================================

Question 1
What is an intersection type, and how is it different from a union?

Answer
An intersection type combines multiple types into one, using the ampersand symbol, and the resulting type must satisfy all of the combined types simultaneously, meaning it needs every property from every type involved. This is the opposite of a union, which only requires satisfying at least one of the types. Intersections are commonly used to compose smaller, focused types into a larger one, similar in spirit to mixins, especially when combining a base type with additional metadata or capability types. If two intersected types have a property with the same name but conflicting, incompatible primitive types, that property collapses to type never, since no value could satisfy both simultaneously.

Example
type Timestamped = { createdAt: Date };
type Named = { name: string };

type Event = Timestamped & Named;

const event: Event = { createdAt: new Date(), name: "Conference" }; // must satisfy both

Follow-up Questions
What happens if two intersected types have conflicting property types?
How do intersections compare to interface extension?
Where have you used intersections to compose types in a real project?

Common Mistakes
❌ Confusing the ampersand (intersection) with the pipe (union) syntax.
❌ Not realizing conflicting primitive property types resolve to never rather than causing an immediate error.

Interview Tips
Interview Tip:
Walk through the "conflicting property becomes never" edge case if asked to go deeper, it's a common follow-up that separates surface-level knowledge from real understanding.

----------------------------------------------------

Question 2
When would you choose an intersection type over extending an interface?

Answer
Interface extension and intersection types often achieve a similar result, combining shapes, but they behave a little differently. Interfaces are generally better when you're modeling a clear "is-a" hierarchy and want the potential for declaration merging, plus interface extension gives clearer error messages when there's a genuine conflict, since TypeScript checks compatibility as it merges rather than silently collapsing to never. Intersections are more flexible because they can combine type aliases, unions, primitives, and function types, things interfaces alone can't extend. I default to interfaces for object shapes that represent a stable domain concept, and reach for intersections when composing more dynamic or utility-style type combinations, especially involving unions.

Example
// Interface extension: cleaner errors, best for object hierarchies
interface Animal { name: string; }
interface Dog extends Animal { breed: string; }

// Intersection: more flexible, can combine with unions or primitives
type ID = string | number;
type TaggedID = ID & { readonly __brand: "UserID" };

Follow-up Questions
Can interfaces extend a union type the way intersections can combine with one?
Why might error messages differ between a broken interface extension and a broken intersection?
What is a "branded type" and how does the TaggedID example demonstrate it?

Common Mistakes
❌ Assuming interfaces and intersections are always fully interchangeable.
❌ Not knowing interfaces can't directly extend a union type, while intersections can combine with one.

Interview Tips
Interview Tip:
The branded type example is a great bonus to mention, it shows awareness of a real advanced pattern used to prevent mixing up primitive IDs of different meanings.

----------------------------------------------------

Question 3
What happens when you intersect two object types that share a property with incompatible types?

Answer
When two intersected types share a property name but the types for that property are fundamentally incompatible primitives, like one being string and the other number, TypeScript resolves that specific property's type to never, because no real value could simultaneously be both a string and a number. Importantly, this usually doesn't throw an immediate compiler error on the type declaration itself; instead, the error surfaces later, whenever you actually try to assign a value to that impossible property, since nothing can satisfy a never type. This is a common source of confusing errors for developers who don't expect a silent never rather than a direct conflict error.

Example
type A = { id: string };
type B = { id: number };

type Combined = A & B; // Combined.id is type 'never'

const value: Combined = { id: "abc" }; // error: Type 'string' is not assignable to type 'never'

Follow-up Questions
Why doesn't TypeScript throw an error at the point where the intersection is declared?
How would you debug a confusing "not assignable to never" error in a large codebase?
How does this differ from how interface extension handles the same conflict?

Common Mistakes
❌ Expecting an immediate, clear error message right where the intersection type is defined.
❌ Spending a long time debugging a never-related error without realizing it traces back to an intersection conflict.

Interview Tips
Interview Tip:
If you've genuinely hit this in a real project, mention it. Debugging a mysterious never type is a rite of passage, and sharing that story adds credibility.

TOPIC 11 - ARRAY BASICS
====================================================

Question 1
What are the different ways to type an array in TypeScript?

Answer
There are two equivalent syntaxes for typing arrays: the shorthand form, which is the element type followed by square brackets, and the generic form, Array<ElementType>. Both compile to exactly the same thing, it's purely a stylistic choice, though the shorthand is far more common in everyday code, while the generic form is sometimes preferred for more complex element types where the square bracket syntax would look cluttered. Arrays can also be typed as a union of element types, meaning the array can freely mix values of any of those types at any position, which is different from a tuple, where each position has its own fixed type.

Example
let names: string[] = ["Afnan", "Sara"];
let scores: Array<number> = [90, 85, 78];
let mixed: (string | number)[] = ["id", 1, "name", 2];

Follow-up Questions
Is there any functional difference between T[] and Array<T>?
How is a typed array different from a tuple?
How do you type a readonly array?

Common Mistakes
❌ Thinking T[] and Array<T> behave differently at compile time; they don't.
❌ Using (string | number)[] when a tuple would actually better represent fixed, ordered data.

Interview Tips
Interview Tip:
Mention that both syntaxes are interchangeable, then explain when you'd personally reach for the generic form, showing you have a stylistic opinion, not just textbook knowledge.

----------------------------------------------------

Question 2
How does TypeScript type array methods like map, filter, and reduce?

Answer
Array methods in TypeScript are fully generic and rely heavily on inference. map takes a callback and returns a new array typed based on whatever the callback returns, so mapping numbers to strings correctly produces a string array without any manual annotation. filter is a bit special because it can act as a type guard when the predicate uses a type-narrowing check, which lets it produce a narrower array type than the input. reduce is the trickiest of the three because its accumulator type and initial value type both need to line up correctly, and if you don't provide an explicit initial value, TypeScript sometimes struggles to infer the accumulator's type correctly, especially when it differs from the array's element type.

Example
const numbers = [1, 2, 3, 4];
const doubled = numbers.map((n) => n * 2); // number[]
const evens = numbers.filter((n) => n % 2 === 0); // number[]
const total = numbers.reduce((sum, n) => sum + n, 0); // number, explicit initial value helps inference

const mixed: (string | number)[] = [1, "two", 3];
const onlyStrings = mixed.filter((x): x is string => typeof x === "string"); // string[], narrowed by predicate

Follow-up Questions
Why does filter sometimes need an explicit type predicate to narrow properly?
What issue can arise with reduce if you omit the initial value?
How does TypeScript infer the return type of chained array methods?

Common Mistakes
❌ Forgetting to add a type predicate to filter when you actually want a narrower resulting array type.
❌ Omitting reduce's initial value and being surprised by resulting type errors.

Interview Tips
Interview Tip:
The filter-with-type-predicate example is one of the best ways to show real fluency, most candidates only know the basic filter usage, not this narrowing trick.

----------------------------------------------------

Question 3
What is the difference between a regular array and a readonly array in TypeScript?

Answer
A regular array allows mutation, you can push, pop, splice, or reassign elements by index. A readonly array, declared either with the ReadonlyArray<T> generic or the shorthand readonly T[] syntax, disables every mutating method at compile time; things like push and splice simply won't exist on the type, and index assignment is blocked. This is purely a compile-time guarantee, just like readonly on object properties, it doesn't freeze the array at runtime. I use readonly arrays for function parameters whenever the function shouldn't need to modify the input, which also communicates intent clearly to anyone reading the function signature.

Example
function printAll(items: readonly string[]) {
  items.push("new"); // error: Property 'push' does not exist on type 'readonly string[]'
  console.log(items.join(", ")); // reading is fine
}

const list: ReadonlyArray<number> = [1, 2, 3];
list[0] = 99; // error: Index signature in type 'readonly number[]' only permits reading

Follow-up Questions
Does a readonly array prevent mutation at runtime, or only at compile time?
Why would you use readonly on a function parameter specifically?
How does readonly array relate to as const on array literals?

Common Mistakes
❌ Assuming readonly arrays are actually frozen and immutable at runtime.
❌ Not using readonly on function parameters even when the function has no reason to mutate the input.

Interview Tips
Interview Tip:
Frame readonly parameters as a form of documentation and API contract, not just a restriction, that framing resonates well with interviewers focused on code design.

TOPIC 12 - READONLY ARRAYS
====================================================

Question 1
How do you convert a mutable array type into a readonly array type, and vice versa?

Answer
To make an array type readonly, you either prefix it with the readonly keyword, use the ReadonlyArray<T> generic, or wrap an existing type with the Readonly<T> utility type, though Readonly<T> only makes the top-level array readonly, not deeply. Going the other direction, from readonly to mutable, requires a type assertion, since there's no clean built-in utility for that specific conversion; you typically cast it back to T[] or spread it into a brand-new array, which actually copies the data and gives you a genuinely separate mutable array.

Example
function toReadonly<T>(arr: T[]): readonly T[] {
  return arr;
}

function toMutable<T>(arr: readonly T[]): T[] {
  return [...arr]; // spreading creates a new, genuinely mutable array
}

const frozen: readonly number[] = [1, 2, 3];
const copy = toMutable(frozen);
copy.push(4); // valid, copy is a new mutable array

Follow-up Questions
Why is spreading preferred over casting when converting readonly back to mutable?
Does casting a readonly array back to T[] provide any real runtime safety?
How deep does the Readonly<T> utility type actually go?

Common Mistakes
❌ Casting a readonly array directly to T[] and still mutating the original underlying array reference.
❌ Assuming Readonly<T> recursively locks nested arrays and objects, it does not by default.

Interview Tips
Interview Tip:
Emphasize that spreading creates an actual new array in memory, whereas casting is just a type-level lie that doesn't protect the original reference at runtime.

----------------------------------------------------

Question 2
Why would you use a readonly array as a function parameter type even if you're passing in a regular mutable array?

Answer
A readonly array parameter is a defensive, self-documenting design choice. Regular mutable arrays are perfectly assignable to a readonly array parameter, since a readonly array is a supertype, anything you can do with a readonly array, you can also do with a mutable one, so there's no compatibility issue in either direction, only that readonly restricts what the function itself is allowed to do internally. This tells both the compiler and anyone reading the function signature that the function promises not to mutate the input, which is especially valuable in larger codebases where you want to guarantee a function has no unexpected side effects on data owned elsewhere.

Example
function sum(numbers: readonly number[]): number {
  return numbers.reduce((total, n) => total + n, 0); // read-only operations are fine
}

const myScores = [10, 20, 30]; // a regular, mutable array
sum(myScores); // valid, mutable arrays are assignable to readonly array parameters

Follow-up Questions
Is it safe to pass a mutable array into a function expecting a readonly array parameter?
How does this pattern help prevent unintended side effects in larger codebases?
Would the reverse, passing a readonly array where a mutable one is expected, also work?

Common Mistakes
❌ Believing readonly array parameters require the caller to also pass a readonly-typed array.
❌ Not applying this pattern in utility or pure functions where it would clearly communicate intent.

Interview Tips
Interview Tip:
Explain the variance direction clearly: mutable arrays can be passed where readonly is expected, but not the other way around, since that asymmetry trips a lot of people up.

TOPIC 13 - TUPLES
====================================================

Question 1
What is a tuple in TypeScript, and how is it different from a regular array?

Answer
A tuple is a fixed-length array where each position has its own specific, known type, unlike a regular array where every element shares the same general type and the length is unbounded. Tuples are useful when you have a small, fixed structure where position carries meaning, like a coordinate pair, or a function that returns exactly two related values, such as a value and an error. At runtime, a tuple is literally just a JavaScript array, TypeScript adds no special runtime behavior, it's purely a compile-time guarantee about length and per-position types.

Example
let coordinate: [number, number] = [10, 20];
let httpResult: [number, string] = [200, "OK"];

httpResult = [200, "OK", "extra"]; // error: source has more elements than target

Follow-up Questions
Are tuples enforced at runtime, or only at compile time?
How do optional elements work within a tuple?
Why would you choose a tuple over an object with named properties?

Common Mistakes
❌ Assuming TypeScript will stop you at runtime from pushing extra elements onto a tuple.
❌ Overusing tuples for data that would be clearer as a named object.

Interview Tips
Interview Tip:
Mention explicitly that a tuple is just an array at runtime with no length enforcement outside the type system, this is a very common follow-up trap.

----------------------------------------------------

Question 2
How does React's useState hook relate to tuples, and why does it return an array instead of an object?

Answer
useState returns a tuple: the first element is the current state value, and the second is the setter function, typed as [T, Dispatch<SetStateAction<T>>]. Returning an array instead of an object is a deliberate design choice that takes advantage of how array destructuring works in JavaScript, you can rename both values freely at the call site, like const [count, setCount] = useState(0), without needing to alias object property names. If useState returned an object instead, you'd be forced to either use the exact property names it defines or explicitly rename them with object destructuring syntax, which is more verbose when you're calling the hook many times with different variable names throughout a component.

Example
function useState<T>(initial: T): [T, (value: T) => void] {
  // simplified conceptual implementation
  let state = initial;
  const setState = (value: T) => { state = value; };
  return [state, setState];
}

const [count, setCount] = useState(0);
const [name, setName] = useState("");

Follow-up Questions
Why is positional destructuring more convenient than named destructuring in this case?
Could useState have been designed to return an object instead? What would change?
What does the actual return type signature of useState look like in React's type definitions?

Common Mistakes
❌ Not recognizing this as one of the most common real-world uses of tuples.
❌ Assuming array destructuring and object destructuring are functionally identical in this context.

Interview Tips
Interview Tip:
This question tests whether you connect abstract TypeScript concepts to tools you use daily. Always tie tuples back to a concrete example like this one.

Question 3
How do you type a tuple with optional or variable-length trailing elements?

Answer
You can mark a specific position in a tuple as optional using a question mark, just like an optional object property, meaning that element and everything after it can be omitted, though optional elements must come after all required ones. For truly variable-length trailing data, tuples support a rest element using the spread syntax, similar to rest parameters in a function, which lets you have a fixed set of required positions followed by an open-ended number of same-typed elements at the end.

Example
type NameParts = [first: string, middle?: string, last?: string];
const twoPart: NameParts = ["Afnan", "Khan"]; // valid, middle and last omitted... wait, this needs positional correctness

type Coordinates3D = [x: number, y: number, ...rest: number[]];
const point: Coordinates3D = [1, 2, 3, 4, 5]; // valid, extra numbers allowed after x and y

Follow-up Questions
Where must optional elements be positioned within a tuple?
How is a rest element in a tuple different from a rest parameter in a function?
Can you name tuple elements for better readability, and does that affect the type itself?

Common Mistakes
❌ Placing a required element after an optional one in a tuple definition, which is not allowed.
❌ Forgetting that named tuple elements are purely for documentation and don't change runtime behavior.

Interview Tips
Interview Tip:
Bring up labeled tuple elements, like [x: number, y: number], as a readability improvement introduced in later TypeScript versions, showing you keep up with language evolution.

TOPIC 14 - PARAMETER ANNOTATIONS
====================================================

Question 1
How do you properly annotate function parameters, and what happens if you don't?

Answer
Function parameters are annotated with a colon followed by the type, right after the parameter name, the same pattern used for variables. If a parameter is left unannotated and TypeScript can't infer it from context, like contextual typing in a callback, it defaults to implicit any, unless the noImplicitAny compiler flag is enabled, in which case TypeScript throws a compile error instead, forcing you to either annotate it explicitly or accept an explicit any. I always keep noImplicitAny on, and I annotate every parameter in exported or public functions, since inference doesn't help other files calling into your function.

Example
function createUser(name: string, age: number, isAdmin: boolean = false) {
  return { name, age, isAdmin };
}

createUser("Afnan", "28", false); // error: '"28"' is not assignable to parameter of type 'number'

Follow-up Questions
What happens to unannotated parameters when noImplicitAny is disabled?
Do parameters ever get inferred automatically without an annotation?
Why is annotating parameters especially important for exported functions?

Common Mistakes
❌ Leaving parameters unannotated in exported functions, since callers get no safety without an explicit contract.
❌ Assuming default parameter values remove the need for a type annotation entirely.

Interview Tips
Interview Tip:
Point out that even with a default value giving TypeScript an inferred type, an explicit annotation is still good practice for public-facing functions since it documents intent clearly.

----------------------------------------------------

Question 2
What is the difference between typing a parameter with a specific interface versus using an inline object type?

Answer
Both achieve the same type checking, but they differ in reusability and readability. A named interface or type alias can be reused across multiple functions, exported for consumers of your module, and gives a clear, semantic name to the shape in error messages and editor tooltips. An inline object type is defined directly in the parameter list and works fine for a one-off function that nobody else needs to reference, but it clutters the function signature and can't be reused elsewhere without duplicating the shape. I default to named types the moment a shape is used in more than one place, or whenever the shape represents a meaningful domain concept worth naming.

Example
// Inline, fine for a single, simple use
function logPoint(point: { x: number; y: number }) { /* ... */ }

// Named, reusable, and clearer intent
interface Point { x: number; y: number; }
function distanceFromOrigin(point: Point): number {
  return Math.sqrt(point.x ** 2 + point.y ** 2);
}

Follow-up Questions
At what point would you refactor an inline object type into a named interface?
Do inline object types show up differently in error messages compared to named types?
Is there a performance difference between inline and named types?

Common Mistakes
❌ Overusing inline object types for shapes that are actually reused in multiple places.
❌ Assuming named types have any runtime cost compared to inline types, they don't, both disappear after compilation.

Interview Tips
Interview Tip:
Frame your answer around maintainability and reusability rather than a hard technical rule, since this is ultimately a design decision, not a compiler restriction.

----------------------------------------------------

Question 3
Can you use destructuring with type annotations in function parameters? How does that syntax work?

Answer
Yes, destructured parameters are annotated by placing the type after the entire destructuring pattern, not on the individual destructured names. This is a syntax detail that often trips people up at first because it looks unusual compared to annotating a normal parameter. It's especially common for functions that accept a single options object, which is a very popular pattern in modern APIs since it makes call sites self-documenting through named arguments instead of relying on positional order.

Example
interface FetchOptions {
  url: string;
  method: "GET" | "POST";
  retries?: number;
}

function fetchData({ url, method, retries = 3 }: FetchOptions) {
  console.log(url, method, retries);
}

fetchData({ url: "/api/users", method: "GET" });

Follow-up Questions
Why is the type annotation placed after the whole destructuring pattern rather than on individual fields?
Why is an options object pattern often preferred over many positional parameters?
How do default values interact with destructured parameters and optional properties?

Common Mistakes
❌ Trying to annotate individual destructured variables directly, which is invalid syntax.
❌ Forgetting to make a property optional in the interface even though a default value is provided in destructuring.

Interview Tips
Interview Tip:
If a function has more than two or three parameters, mention that you'd refactor it into a single options object, that's a design opinion interviewers like to hear articulated clearly.



====================================================
TOPIC 15 - OPTIONAL & DEFAULT PARAMETERS
====================================================

Question 1
What is the difference between an optional parameter and a default parameter?

Answer
An optional parameter, marked with a question mark, can be omitted entirely by the caller, and inside the function its type automatically includes undefined, so you have to handle the missing case yourself. A default parameter, on the other hand, provides a fallback value that's used whenever the caller omits the argument or explicitly passes undefined, and inside the function, the parameter's type is based on the default value combined with whatever type you'd otherwise annotate, without needing to include undefined, since the default guarantees a real value will always be present. In practice, I use default parameters whenever there's a sensible fallback, and optional parameters when there genuinely isn't one and the absence itself needs to be handled explicitly.

Example
function greetOptional(name?: string) {
  return `Hello, ${name ?? "Guest"}`; // must handle undefined manually
}

function greetDefault(name: string = "Guest") {
  return `Hello, ${name}`; // name is guaranteed to be a string here
}

Follow-up Questions
Why doesn't a default parameter's type include undefined inside the function body?
Can a parameter be both optional and have a default value at the same time?
Where must optional and default parameters be positioned relative to required ones?

Common Mistakes
❌ Forgetting to handle the undefined case for an optional parameter within the function body.
❌ Placing an optional or default parameter before a required parameter in the parameter list, which is invalid.

Interview Tips
Interview Tip:
Explain that default parameters effectively "absorb" the undefined case for you, which is exactly why their inferred type inside the function is narrower than an optional parameter's type.

----------------------------------------------------

Question 2
Can default parameter values reference earlier parameters in the same function?

Answer
Yes, a default parameter expression can reference any parameter that comes before it in the parameter list, since parameters are evaluated left to right, and each earlier parameter is already in scope by the time a later default value expression runs. This is useful for parameters that should logically derive from another parameter unless explicitly overridden. It cannot reference parameters that come after it, since those haven't been evaluated yet at that point.

Example
function createRange(start: number, end: number = start + 10) {
  return { start, end };
}

createRange(5); // { start: 5, end: 15 }
createRange(5, 20); // { start: 5, end: 20 }

Follow-up Questions
What would happen if a default value tried to reference a parameter defined after it?
Is this pattern common in real-world APIs you've worked with?
How does this interact with destructured default parameters?

Common Mistakes
❌ Trying to reference a later parameter from an earlier parameter's default expression.
❌ Not realizing this ordering dependency exists at all and being surprised when it fails.

Interview Tips
Interview Tip:
This is a fairly advanced, lesser-known detail. Bringing it up unprompted, even briefly, shows genuine hands-on experience rather than surface-level familiarity.

----------------------------------------------------

Question 3
How do optional parameters affect a function's call signature when working with function overloads or callback types?

Answer
When a parameter is optional, it effectively creates multiple valid call signatures for that function, one where the argument is provided and one where it's omitted, similar in spirit to writing explicit overloads. This matters most when passing functions around as values, for example assigning a function with fewer parameters to a variable or parameter typed to expect more, which TypeScript actually allows, because a function that ignores extra arguments is still compatible; but the reverse isn't generally true, a function requiring more parameters than the expected type provides is not assignable, since it would be called with missing arguments.

Example
type ClickHandler = (event: MouseEvent, index: number) => void;

const handler: ClickHandler = (event) => {
  console.log(event.type); // valid, extra parameter 'index' can simply be ignored
};

const invalidHandler: ClickHandler = (event, index, extra) => {}; // error: too many required parameters

Follow-up Questions
Why can a function with fewer parameters satisfy a type expecting more parameters?
How does this relate to how array callback methods like forEach or map are typed?
What would break if this compatibility rule worked the other way around?

Common Mistakes
❌ Assuming a callback's parameter count must exactly match the expected function type.
❌ Not understanding why array methods let you omit the index and array arguments in your callback.

Interview Tips
Interview Tip:
Tie this directly back to Array.prototype.forEach or map, where developers routinely write (item) => {...} and omit the index and array parameters entirely. It's a pattern used every day without most people realizing why it type-checks.


====================================================
TOPIC 16 - REST TUPLES
====================================================

Question 1
How do rest parameters work in TypeScript, and how are they typed?

Answer
Rest parameters let a function accept an indefinite number of arguments, collected into a single array, using the triple-dot syntax before the final parameter name. You type a rest parameter as an array type, since that's exactly what it becomes inside the function, every extra argument passed by the caller gets collected into that array in order. Rest parameters must be the last parameter in the list, since there's no way to know where a variable-length group ends if something else followed it.

Example
function sum(...numbers: number[]): number {
  return numbers.reduce((total, n) => total + n, 0);
}

sum(1, 2, 3, 4); // 10
sum(); // 0, empty array is valid

Follow-up Questions
Why must a rest parameter always be the last parameter in a function?
Can you combine regular parameters with a rest parameter?
How is a rest parameter different from just accepting a single array argument?

Common Mistakes
❌ Trying to place a rest parameter anywhere other than the last position.
❌ Confusing rest parameters, which collect arguments, with spread syntax, which expands them.

Interview Tips
Interview Tip:
Clearly separate "rest" from "spread" in your explanation, they use identical syntax but do opposite things, and interviewers often ask a quick follow-up to check you know the difference.

----------------------------------------------------

Question 2
What are variadic tuple types, and how do they improve typing for functions with rest parameters?

Answer
Variadic tuple types let you use the spread syntax inside a tuple type itself, allowing you to combine fixed, known positions with a genuinely flexible, generic rest portion, all while preserving each individual type rather than collapsing everything into one union array type. This became especially powerful for typing utility functions like a custom curry or bind implementation, where you want to say "the first argument is this specific type, and the rest depend on whatever's passed to a different function," something that older, simpler rest parameter typing couldn't express precisely.

Example
function concat<T extends unknown[], U extends unknown[]>(arr1: [...T], arr2: [...U]): [...T, ...U] {
  return [...arr1, ...arr2];
}

const result = concat([1, 2], ["a", "b"]); // typed as [number, number, string, string]

Follow-up Questions
How do variadic tuples differ from a simple rest parameter typed as unknown[]?
Where have you seen variadic tuples used in real utility libraries?
How does this feature relate to typing something like Function.prototype.bind?

Common Mistakes
❌ Typing flexible tuple-combining functions with a loose unknown[] rest type, losing precision.
❌ Not recognizing variadic tuples as the mechanism behind strongly typed function composition utilities.

Interview Tips
Interview Tip:
This is a genuinely advanced topic; if the interviewer brings it up, mention that libraries like typed Redux middleware or strongly typed event emitters rely heavily on this feature.

----------------------------------------------------

Question 3
How would you type a function that takes a required first argument followed by a variable number of additional arguments of the same type?

Answer
You combine a regular required parameter with a rest parameter typed as an array of that same type, or a related type. This pattern is extremely common for utility functions like a logger that always needs a required message but accepts any number of additional context values, or a math function requiring at least one number followed by any additional numbers to combine with it.

Example
function logWithContext(message: string, ...context: unknown[]): void {
  console.log(message, ...context);
}

function minimum(first: number, ...rest: number[]): number {
  return rest.reduce((min, n) => Math.min(min, n), first);
}

logWithContext("User logged in", { userId: 42 }, "extra info");
minimum(5, 2, 9, 1); // 1

Follow-up Questions
How would you enforce that at least two arguments are required, not just one, using tuple types?
Why is unknown often a better rest parameter type than any for something like a logger?
How does TypeScript infer the return type when combining a required parameter with a rest parameter in a reducer-like function?

Common Mistakes
❌ Typing the rest parameter as any[] instead of a safer, more specific type like unknown[] or a matching type.
❌ Forgetting rest parameters default to an empty array if the caller passes nothing beyond the required arguments.

Interview Tips
Interview Tip:
If asked to enforce a stricter minimum count than one required argument, mention that you can use a tuple type like [number, number, ...number[]] to require at least two arguments upfront.


====================================================
TOPIC 17 - RETURN TYPES
====================================================

Question 1
Should you always explicitly annotate a function's return type, or let TypeScript infer it?

Answer
For most internal, small functions, I let TypeScript infer the return type, since it's usually accurate and keeps the code less cluttered. For exported functions and public APIs, though, I explicitly annotate the return type, for a very practical reason: if the function's implementation changes and accidentally starts returning a different or wider type than intended, an explicit return type turns that into a compile error right at the function definition, rather than letting the wrong inferred type silently propagate outward to every caller. It also makes the function's contract clear to anyone reading just the signature, without needing to read the implementation.

Example
// Internal helper, inference is fine
function double(n: number) {
  return n * 2;
}

// Public API, explicit return type protects the contract
export function fetchUserById(id: string): Promise<User | null> {
  return db.users.findOne({ id });
}

Follow-up Questions
What risk does relying purely on inference introduce for exported functions?
Does an explicit return type ever help with self-documentation even if inference would be correct?
How does noImplicitReturns relate to return type consistency?

Common Mistakes
❌ Never annotating return types on exported functions, letting silent type drift happen over time.
❌ Over-annotating every trivial internal function's return type when inference already gives an accurate, narrow result.

Interview Tips
Interview Tip:
Frame this as a "public API surface versus internal implementation detail" distinction, that framing sounds intentional and experienced rather than like a blanket rule you memorized.

----------------------------------------------------

Question 2
How do you type a function that can return early with different types depending on a condition?

Answer
When a function has multiple return statements with different types, TypeScript automatically infers the return type as a union of all the possible returned types, without you needing to do anything special. If you want to be explicit, or the inferred union is too broad for what you actually intend, you annotate the return type directly with the union you want to allow, and the compiler will then verify every return statement actually matches one of those types. This is very common in functions that either return a successful result or an error indicator, like null or a custom error object.

Example
function parseAge(input: string): number | null {
  const parsed = Number(input);
  if (Number.isNaN(parsed) || parsed < 0) {
    return null;
  }
  return parsed;
}

Follow-up Questions
What happens if one return statement doesn't match the declared return type union?
How does this connect back to discriminated unions for more complex return shapes?
Would you prefer throwing an error over returning null in some cases? Why?

Common Mistakes
❌ Letting the inferred return type union grow unexpectedly wide without checking if that's actually intended.
❌ Mixing null returns and thrown exceptions inconsistently within the same function for similar failure cases.

Interview Tips
Interview Tip:
If discussing error handling, briefly compare returning null/error objects versus throwing exceptions, and explain your personal preference with a reason, that shows design maturity beyond just syntax knowledge.

----------------------------------------------------

Question 3
How do you correctly type the return value of an async function?

Answer
An async function always returns a Promise, no exceptions, even if the function body seems to return a plain value directly, JavaScript automatically wraps that value in a resolved promise. So when annotating an async function's return type, you always wrap the actual resolved value type in Promise<>, not the raw type itself. TypeScript will actually catch you if you try to annotate an async function's return type as the raw value type instead of a Promise, since that wouldn't match what the function genuinely returns at runtime.

Example
async function fetchUserName(id: string): Promise<string> {
  const response = await fetch(`/api/users/${id}`);
  const data = await response.json();
  return data.name; // return type here contributes to the resolved value inside Promise<string>
}

// Incorrect: this would be a type error
// async function broken(): string { return "hello"; }

Follow-up Questions
What actually happens if you try to annotate an async function's return type without wrapping it in Promise?
How does the Awaited utility type relate to unwrapping this Promise type?
Does an async function that doesn't explicitly return anything still return a Promise?

Common Mistakes
❌ Annotating an async function's return type as the raw value instead of wrapping it in Promise.
❌ Forgetting that an async function with no explicit return statement still returns Promise<void>.

Interview Tips
Interview Tip:
If asked a quick follow-up about unwrapping the type, mention the Awaited<T> utility type by name, it directly complements this topic and shows you're already thinking a step ahead.



====================================================
TOPIC 18 - INTERFACE BASICS
====================================================

Question 1
What is an interface in TypeScript, and what is it typically used for?

Answer
An interface defines the shape of an object: what properties it has, their types, and what methods it exposes. It's purely a compile-time construct, it doesn't exist in the compiled JavaScript output at all, it exists solely to describe structure for the type checker. Interfaces are the go-to tool for defining the contract of an object, a class's public API, or the props of a component. They support extension, so one interface can build on another, and they support declaration merging, meaning multiple interface declarations with the same name in the same scope automatically combine into one, which is a genuinely unique feature compared to type aliases.

Example
interface User {
  id: string;
  email: string;
  isActive: boolean;
  deactivate(): void;
}

class Account implements User {
  constructor(public id: string, public email: string, public isActive: boolean) {}
  deactivate() { this.isActive = false; }
}

Follow-up Questions
Does an interface produce any actual JavaScript output after compilation?
What is declaration merging and why is it unique to interfaces?
Can an interface describe a function type as well as an object shape?

Common Mistakes
❌ Believing interfaces exist in the compiled JavaScript in any form.
❌ Not knowing that interfaces, unlike type aliases, can merge across multiple declarations.

Interview Tips
Interview Tip:
Always mention that interfaces compile away completely. It's a small detail, but confusing this with runtime constructs like classes is a common beginner mistake interviewers listen for.

----------------------------------------------------

Question 2
Can an interface extend multiple other interfaces at once?

Answer
Yes, an interface can extend more than one interface simultaneously by separating each one with a comma after the extends keyword. The resulting interface requires every member from all the extended interfaces combined, similar in effect to an intersection type, but expressed through inheritance syntax instead. This is useful for composing smaller, focused interfaces into a larger, more complete one, which follows the interface segregation idea from object-oriented design, keeping each individual interface small and purposeful.

Example
interface Timestamped {
  createdAt: Date;
  updatedAt: Date;
}

interface Named {
  name: string;
}

interface Product extends Timestamped, Named {
  price: number;
}

const item: Product = {
  name: "Laptop",
  price: 999,
  createdAt: new Date(),
  updatedAt: new Date(),
};

Follow-up Questions
How does extending multiple interfaces compare to combining types with an intersection?
What happens if two extended interfaces have conflicting property types?
Why might you prefer several small interfaces over one large one?

Common Mistakes
❌ Assuming an interface can only extend a single parent interface.
❌ Designing overly large, monolithic interfaces instead of composing smaller, focused ones.

Interview Tips
Interview Tip:
Mention "interface segregation," it's one of the SOLID principles, and connecting TypeScript syntax back to established design principles is a strong senior-level signal.

----------------------------------------------------

Question 3
What is declaration merging, and how does it work with interfaces?

Answer
Declaration merging is a TypeScript feature where multiple declarations with the same name automatically combine into a single definition, and interfaces are the most common example of this. If you declare an interface with the same name more than once, even in completely separate files, TypeScript merges all the members together into one interface, rather than throwing a duplicate declaration error the way you'd get with a type alias. This is genuinely useful when extending third-party library types, for example adding a custom property onto Express's Request interface, without needing to modify the original library's source code.

Example
interface Window {
  myCustomGlobal: string;
}

// Somewhere else in the codebase, or in a library's own types
interface Window {
  anotherCustomProperty: number;
}

// Both properties now exist on the merged Window interface
window.myCustomGlobal = "hello";
window.anotherCustomProperty = 42;

Follow-up Questions
Why can't type aliases merge the way interfaces do?
What's a real-world scenario where you'd rely on declaration merging?
Are there any risks or downsides to declaration merging in a large codebase?

Common Mistakes
❌ Trying to achieve the same merging behavior with a type alias, which throws a duplicate identifier error instead.
❌ Overusing declaration merging casually, since unintended merges across a large codebase can be genuinely confusing to trace.

Interview Tips
Interview Tip:
Give the concrete example of augmenting Express's Request type to add a custom "user" property after authentication middleware runs, it's a widely recognized real-world use case.


====================================================
TOPIC 19 - TYPE ALIASES
====================================================

Question 1
What is a type alias, and how is it different from just using the type directly everywhere?

Answer
A type alias gives a name to any type, whether that's a primitive, a union, an object shape, a tuple, or a complex generic type, using the type keyword. It doesn't create a genuinely new type, it's just a reusable reference to an existing type definition. The real benefit is avoiding repetition and improving readability: instead of writing out a complex union or object shape every time you need it, you write it once, give it a meaningful name, and reuse that name everywhere, which also makes future changes much easier since you only update the definition in one place.

Example
type ID = string | number;
type Status = "pending" | "approved" | "rejected";

interface Order {
  id: ID;
  status: Status;
}

function findOrder(id: ID): Order | undefined { /* ... */ return undefined; }

Follow-up Questions
Does a type alias create a genuinely distinct type, or is it purely a label?
Can a type alias represent a union type the way an interface cannot?
What kinds of types can a type alias represent that an interface can't?

Common Mistakes
❌ Believing type aliases create nominal, distinct types rather than just naming existing structural types.
❌ Not realizing type aliases can represent unions, tuples, and primitives, not just object shapes.

Interview Tips
Interview Tip:
Clarify that a type alias is structurally identical to whatever it points to, TypeScript doesn't treat two different aliases pointing to the same shape as incompatible.

----------------------------------------------------

Question 2
Can a type alias be recursive, referencing itself?

Answer
Yes, type aliases can be recursive, referencing themselves within their own definition, which is essential for modeling naturally recursive structures like JSON values, tree structures, or linked lists. TypeScript handles this fine as long as the recursion is structured properly and eventually resolves, direct self-reference for object or array types works well, though deeply recursive conditional types can sometimes hit the compiler's recursion depth limits on extremely complex cases.

Example
type Json = string | number | boolean | null | Json[] | { [key: string]: Json };

const data: Json = {
  name: "Afnan",
  active: true,
  tags: ["dev", "typescript"],
  nested: { level: 1, values: [1, 2, 3] },
};

Follow-up Questions
Where have you used a recursive type in a real project?
What happens if a recursive type never actually resolves to a base case?
How would you model a tree structure using a recursive type alias?

Common Mistakes
❌ Assuming type aliases can't reference themselves at all.
❌ Writing a recursive type without a proper base case, leading to compiler recursion errors on deeply complex cases.

Interview Tips
Interview Tip:
The Json type example is extremely well-known in the TypeScript community. Being able to write it from memory is a strong, memorable way to answer this question.

----------------------------------------------------

Question 3
When should you prefer a type alias over an interface, and when is it the other way around?

Answer
I reach for a type alias when I need to represent something that isn't a plain object shape, like a union, a tuple, a function type, or a mapped or conditional type, since interfaces can't express those directly. I reach for an interface when modeling a plain object shape, especially one that represents a class's contract or something that might need to be extended or merged later, since interfaces have clearer extension syntax and support declaration merging. For simple object shapes, either works, and it becomes a team convention choice; a lot of style guides just default to interface for objects and type for everything else, which is roughly the convention I follow too.

Example
// Type alias: union, not expressible as an interface
type Result<T> = { success: true; data: T } | { success: false; error: string };

// Interface: plain object shape, extendable
interface ApiClientConfig {
  baseUrl: string;
  timeout?: number;
}
interface AuthenticatedApiClientConfig extends ApiClientConfig {
  token: string;
}

Follow-up Questions
What kinds of types can only be expressed with a type alias, not an interface?
Is there a meaningful performance difference between the two at compile time?
What convention does your team, or would you, adopt for choosing between them?

Common Mistakes
❌ Treating this as a strict technical rule instead of acknowledging it's largely a convention with some genuine capability differences.
❌ Not being able to name a concrete case where only a type alias would work, like a union type.

Interview Tips
Interview Tip:
Give a clear, opinionated rule of thumb, "objects and contracts use interface, everything else uses type", then immediately back it up with the union example, since interfaces genuinely cannot express unions.


====================================================
TOPIC 20 - INTERFACES VS TYPES
====================================================

Question 1
What are the concrete technical differences between an interface and a type alias, beyond just style preference?

Answer
There are a few real, technical differences. First, interfaces support declaration merging, multiple declarations with the same name combine automatically, while type aliases throw a duplicate identifier error if declared twice. Second, interfaces can only describe object shapes, function types, and class contracts, while type aliases can represent unions, intersections, tuples, primitives, mapped types, and conditional types, things interfaces simply cannot express. Third, extending an interface with an incompatible member typically gives a clearer, more direct error message, whereas an intersection type combining conflicting types often just quietly collapses that property to never instead. In modern TypeScript, performance differences between the two are effectively negligible for most codebases.

Example
// Only possible with type alias
type Coordinates = [number, number];
type Handler = (event: Event) => void;
type Status = "active" | "inactive";

// Declaration merging, only possible with interface
interface Config { debug: boolean; }
interface Config { verbose: boolean; }
// merged: { debug: boolean; verbose: boolean }

Follow-up Questions
Can you give an example of something a type alias can do that an interface fundamentally cannot?
Why do incompatible interface extensions produce clearer errors than incompatible intersections?
Has the TypeScript team's official guidance on this topic changed over time?

Common Mistakes
❌ Claiming there is "no real difference" between the two, which undersells genuine technical distinctions.
❌ Not being able to give a concrete example of a type-alias-only capability, like unions or tuples.

Interview Tips
Interview Tip:
Structure your answer around three clear differences: merging, expressiveness, and error clarity. Giving a structured, numbered answer here reads as more senior than a rambling comparison.

----------------------------------------------------

Question 2
Which convention do major companies and style guides typically recommend, interface or type, and why?

Answer
Practices vary, but a common convention, including guidance historically associated with tools like the TypeScript ESLint recommended rules, favors using interface for object shapes by default, largely because of clearer extension error messages and the flexibility of declaration merging for consumers of a library. That said, plenty of large codebases, including parts of major open-source projects, prefer type consistently for everything, valuing consistency and the broader expressive power of type aliases over the specific benefits interfaces offer. The honest answer is that there is no single industry-wide consensus, it's a team-level convention decision, and what actually matters most is picking one approach and staying consistent across the codebase.

Example
// Interface-first convention
interface ButtonProps {
  label: string;
  onClick: () => void;
}

// Type-first convention, same shape
type ButtonProps = {
  label: string;
  onClick: () => void;
};

Follow-up Questions
What convention have you personally used on past projects, and why?
Would your answer change if you were building a public library others would consume, versus an internal app?
How do you handle enforcing a chosen convention across a team, linting or code review?

Common Mistakes
❌ Presenting one convention as objectively, universally correct rather than acknowledging it's a team decision.
❌ Not having a personal, defensible opinion when asked directly what you'd choose.

Interview Tips
Interview Tip:
It's fine, and even preferred, to state your own default convention with reasoning, interviewers are more interested in whether you can reason about trade-offs than in which specific answer you land on.

----------------------------------------------------

Question 3
If you're building a public library, does it matter whether you expose your types as interfaces or type aliases?

Answer
It can matter more than in an internal app, because consumers of a public library might want to extend or augment your types, and interfaces make that significantly easier through both the extends keyword and declaration merging, meaning a consumer can add properties to your exported interface from their own code without modifying your library at all. Type aliases don't support that kind of external augmentation. So for anything meant to be extensible by consumers, like configuration objects or plugin interfaces, I'd lean toward interface specifically for that flexibility, while still using type aliases internally wherever their extra expressiveness, like unions, is genuinely needed.

Example
// library.d.ts
interface PluginOptions {
  name: string;
}

// consumer's own code, augmenting the library's interface
interface PluginOptions {
  timeout: number; // now required wherever PluginOptions is used
}

Follow-up Questions
Why can't consumers augment a type alias the same way they can an interface?
Can you think of a real open-source library that relies on this kind of augmentation pattern?
Would this consideration change your answer to the previous convention question?

Common Mistakes
❌ Not distinguishing between "internal app" and "public library" contexts when discussing this trade-off.
❌ Forgetting that this augmentation capability is exactly why many typed libraries expose interfaces instead of type aliases for their configuration objects.

Interview Tips
Interview Tip:
Mention Express's Request interface augmentation pattern again here if it hasn't come up yet, it's the textbook real-world example of why libraries often choose interfaces for anything meant to be extended by consumers.

TOPIC 21 - INDEX SIGNATURES
====================================================

Question 1
What is an index signature, and when would you use one?

Answer
An index signature lets you type an object whose exact property names aren't known ahead of time, but whose keys all share a common type, usually string or number, and whose values all share a common type too. It's written inside the type or interface as a bracket-wrapped key name and its type, followed by the value type. This is useful for things like a dictionary, a lookup table, or a dynamic configuration object, where you know the general shape of the data but not the specific property names in advance.

Example
interface WordCount {
  [word: string]: number;
}

const counts: WordCount = {
  typescript: 12,
  javascript: 8,
};

counts.python = 5; // valid, matches the index signature
counts.python = "five"; // error: not assignable to type 'number'

Follow-up Questions
Can an index signature coexist with specific, named properties on the same interface?
What's the difference between a string index signature and a number index signature?

Question 2
Can an interface with an index signature also have specific, explicitly named properties? What are the rules?

Answer
Yes, but every explicitly named property's type must be compatible with the index signature's value type, because as far as the type system is concerned, every named property is also technically covered by that same index signature. If a named property's type doesn't fit within what the index signature allows, TypeScript throws a compile error, since it would create an internal contradiction about what values are valid at that key.

Example
interface Config {
  [key: string]: string | number; // general index signature
  name: string; // valid, string fits within string | number
  version: number; // valid, number fits within string | number
  isDebug: boolean; // error: 'boolean' is not assignable to index type 'string | number'
}

Follow-up Questions

❌ Not knowing that widening the index signature's value type, often to a union, is the typical fix.

Interview Tips
Interview Tip:

Question 3
What is the difference between an index signature and the Record<K, V> utility type?

Answer
They accomplish nearly the same goal but differ in syntax and flexibility. Record<K, V> is a built-in generic utility type that generates an object type with keys from K and values of type V, and K is commonly a union of string literals rather than just the general string type, which lets you enforce a specific, closed set of keys while still getting the dictionary-style value typing. A traditional index signature, by contrast, always uses the general string or number as the key type, it can't restrict keys to a specific literal union the way Record can. For that reason, when I know the exact set of valid keys, I reach for Record, and I use a raw index signature only when keys are genuinely open-ended and unpredictable.

Example
type Role = "admin" | "editor" | "viewer";

type Permissions = Record<Role, boolean>;
// equivalent to: { admin: boolean; editor: boolean; viewer: boolean }

const perms: Permissions = { admin: true, editor: false, viewer: true };

Follow-up Questions

Common Mistakes
❌ Using a raw index signature with string keys when the actual set of valid keys is small and known, missing out on Record's stricter safety.
❌ Not knowing Record is itself built using a mapped type under the hood.

Interview Tips
Interview Tip:
Mention that Record is implemented as { [P in K]: T } internally, connecting this topic directly to mapped types shows a well-connected understanding of the type system.

TOPIC 22 - TYPEOF / DATE / INSTANCEOF
====================================================

Question 1
How is the "typeof" keyword used differently in TypeScript's type system compared to JavaScript's runtime typeof operator?

Answer
In JavaScript, typeof is a runtime operator that returns a string describing a value's type, like "string" or "object". TypeScript reuses the same keyword but gives it a second meaning at the type level: when used inside a type position, typeof takes an existing variable, function, or object and extracts its statically known type, letting you derive a type directly from a value instead of writing it out separately by hand. These are two genuinely different mechanisms that just happen to share a keyword, one runs and returns a string at runtime, the other runs during type checking and produces an actual type.

Example
const user = { name: "Afnan", age: 28 };
type UserType = typeof user; // { name: string; age: number }

console.log(typeof user); // "object", the runtime JavaScript typeof

function greet(name: string) { return `Hi, ${name}`; }
type GreetFn = typeof greet; // (name: string) => string

Follow-up Questions

Common Mistakes
❌ Confusing the type-level typeof with the runtime typeof, they behave completely differently despite the shared keyword.
❌ Manually re-declaring a type that already exists implicitly on a value, instead of just deriving it with typeof.

Interview Tips
Interview Tip:
Give both examples side by side, the runtime typeof and the type-level typeof, in the same answer. It's the clearest way to show you understand they're unrelated mechanisms.

Question 2
How do you correctly type Date objects, and what are common pitfalls when working with dates in TypeScript?

Answer
Date is a built-in global class in JavaScript, and TypeScript has full built-in type definitions for it, so you type a date-holding variable simply as Date, no special handling needed. The common pitfalls aren't really about TypeScript's typing of Date itself, but about a mismatch between what you expect and what you actually get: JSON doesn't have a native date type, so a Date sent through an API response comes back as a plain string after JSON parsing, not an actual Date instance, even if your interface optimistically types that field as Date. This is a classic runtime-versus-compile-time mismatch, the compiler trusts your annotation, but the real value coming from fetch().json() is a string until you explicitly convert it.

Example
interface Event {
  name: string;
  startsAt: Date; // this is a lie if the data comes straight from a JSON API response
}

async function getEvent(): Promise<Event> {
  const response = await fetch("/api/event");
  const data = await response.json();
  return { ...data, startsAt: new Date(data.startsAt) }; // must convert manually
}

Follow-up Questions

Interview Tips

Question 3
How does the instanceof operator work for narrowing types in TypeScript?

Answer
instanceof checks at runtime whether an object's prototype chain includes a specific class's prototype, and TypeScript uses that same check as a narrowing mechanism at the type level. When you have a union of class instance types and check a value with instanceof SomeClass inside an if statement, TypeScript narrows the type within that block to specifically that class, letting you safely access members unique to it. This only works reliably with actual classes, since plain object literals and interfaces don't have a real runtime prototype chain to check against, instanceof has nothing to verify for those.

Example
class ApiError extends Error {
  constructor(public statusCode: number, message: string) {
    super(message);
  }
}

function handleError(error: Error) {
  if (error instanceof ApiError) {
    console.log(error.statusCode); // narrowed, statusCode is accessible here
  } else {
    console.log(error.message); // still just a generic Error
  }
}

Follow-up Questions

How does instanceof narrowing compare to using the "in" operator for narrowing?

Common Mistakes
❌ Trying to use instanceof to narrow a plain object type or interface instead of an actual class.
❌ Forgetting the cross-realm caveat, where instanceof can behave unexpectedly across different JavaScript execution contexts.

Interview Tip:

TOPIC 23 - IN OPERATOR & OPTIONAL NULLISH
====================================================

Question 1
How does the "in" operator work as a type-narrowing technique?

Answer
The "in" operator checks at runtime whether a specific property exists on an object, and TypeScript uses this same check to narrow a union type. When you check "propertyName" in someValue inside a conditional, TypeScript narrows someValue, within that branch, down to whichever member or members of the union actually have that property defined. This is especially useful for narrowing a union of plain object types, like a discriminated union that doesn't have a shared literal tag field but does have differing property names between its variants.

Example
interface Cat { meow(): void; }
interface Dog { bark(): void; }

function makeSound(animal: Cat | Dog) {
  if ("meow" in animal) {
    animal.meow(); // narrowed to Cat
  } else {
    animal.bark(); // narrowed to Dog
  }
}

Follow-up Questions

Would this work if both interfaces shared the same property name?

Common Mistakes
❌ Using "in" narrowing when the union types share overlapping property names, which prevents clean narrowing.
❌ Forgetting that "in" checks actual runtime property existence, not just the compile-time type shape.

Interview Tips
Interview Tip:
Contrast "in" narrowing with instanceof narrowing directly, "in" works for plain object shapes without a class, while instanceof requires an actual class hierarchy, this comparison shows a complete mental model.

Question 2
What is optional chaining, and how does it interact with TypeScript's type system?

Answer
Optional chaining, written as a question mark before a dot, safely accesses a nested property without throwing an error if any part of the chain is null or undefined, short-circuiting and returning undefined immediately instead of crashing. TypeScript fully understands optional chaining and automatically types the resulting expression as the original property's type unioned with undefined, since that's exactly what could actually happen at runtime. This makes deeply nested, potentially-missing data much safer and far less verbose to access than writing out a long chain of manual null checks.

Example
interface UserProfile {
  address?: {
    city?: string;
  };
}

function getCity(user: UserProfile): string | undefined {
  return user.address?.city; // safely returns undefined if address is missing
}

Follow-up Questions
How does TypeScript type the result of an optional chaining expression?
Does optional chaining work with function calls as well as property access?
How does optional chaining interact with array indexing?

Common Mistakes
❌ Overusing optional chaining everywhere as a substitute for actually fixing genuinely required, missing data upstream.
❌ Forgetting that the result type always includes undefined, and not handling that downstream.

Interview Tips
Interview Tip:
Mention that optional chaining should complement good data modeling, not replace it, if a value should never realistically be missing, the real fix is making it required, not sprinkling question marks everywhere.

----------------------------------------------------

Question 3
What is the nullish coalescing operator, and how is it different from the logical OR operator for providing default values?

Answer
The nullish coalescing operator, written as two question marks, returns its right-hand side only when the left-hand side is specifically null or undefined, and returns the left-hand side otherwise. This is meaningfully different from the logical OR operator, which returns the right-hand side for any falsy value at all, including 0, an empty string, or false, not just null or undefined. This distinction matters enormously for numeric or boolean values where 0 or false are perfectly legitimate, intentional values that shouldn't be silently replaced by a default.

Example
function getQuantity(quantity: number | undefined): number {
  return quantity ?? 10; // only falls back to 10 if quantity is null or undefined
}

getQuantity(0); // returns 0, correctly preserved
// Using OR instead would incorrectly return 10 here:
// return quantity || 10;

Follow-up Questions
Why is the OR operator dangerous for providing defaults on numeric or boolean values?
Can nullish coalescing be combined with optional chaining in the same expression?
Does TypeScript narrow types differently based on ?? versus ||?

Common Mistakes
❌ Using || for default values on fields that could legitimately be 0, false, or an empty string.
❌ Not recognizing this as one of the most common real-world sources of subtle logic bugs in JavaScript and TypeScript code.

Interview Tips
Interview Tip:
The quantity-equals-zero example is the single most convincing, memorable way to demonstrate why ?? exists. Always use a concrete falsy-but-valid value in your example, not an abstract explanation.

TOPIC 24 - GENERICS
====================================================

Question 1
What are generics in TypeScript, and why do we need them?

Answer
Generics let you write a function, interface, or class that works with a variety of types while still preserving type information, instead of throwing that information away with any or duplicating the same logic for every specific type. A generic is essentially a type-level variable, written inside angle brackets, that gets filled in with an actual type either when the caller explicitly provides one, or automatically inferred from the arguments passed in. The core problem generics solve is reusability without sacrificing safety, without generics, you'd either write the same function multiple times for different types, or use any and lose all type checking entirely.

Example
function identity<T>(value: T): T {
  return value;
}

const num = identity(42); // T inferred as number, returns number
const str = identity("hello"); // T inferred as string, returns string

Follow-up Questions
How is a generic type different from using "any"?
Where does TypeScript infer the generic type from if you don't specify it explicitly?
Can generics be used on interfaces and classes, not just functions?

Common Mistakes
❌ Reaching for any when a generic would preserve type safety while still allowing flexibility.
❌ Not understanding that T is just a placeholder name, any valid identifier works, T is just convention.

Interview Tips
Interview Tip:
Explain generics as "type-safe placeholders for types," and immediately contrast with any to make the value proposition crystal clear, this contrast is what interviewers are really listening for.

----------------------------------------------------

Question 2
How does TypeScript infer generic type parameters when you call a generic function without explicitly specifying them?

Answer
TypeScript looks at the actual arguments passed into the function call and works backward to figure out what the generic type parameter must be, based on where that parameter appears in the function's parameter types. If a generic type is used in multiple parameters, TypeScript tries to find a type that satisfies all of them, often the best common type across all the usages. If inference is ambiguous, or the generic parameter doesn't appear in any parameter, only in the return type for example, you generally have to specify the type explicitly, since there's nothing for the compiler to infer it from.

Example
function firstElement<T>(arr: T[]): T {
  return arr[0];
}

const first = firstElement([1, 2, 3]); // T inferred as number

function pair<T>(a: T, b: T): [T, T] {
  return [a, b];
}

const p = pair(1, "two"); // T inferred as string | number, the best common type

Follow-up Questions
What happens when a generic type parameter doesn't appear in any function parameter?
How does TypeScript handle inference when multiple parameters could imply different types?
When would you explicitly specify a generic type argument instead of relying on inference?

Common Mistakes
❌ Being surprised when a generic infers a wider union type than expected across mismatched arguments.
❌ Not knowing how to explicitly provide a generic type argument when inference alone isn't enough.

Interview Tips
Interview Tip:
Show both an inferred call and an explicit call, like firstElement<number>([1,2,3]), to demonstrate you know both paths exist and when each is appropriate.

----------------------------------------------------

Question 3
Can you use generics with interfaces and classes, not just standalone functions?

Answer
Yes, generics apply to interfaces and classes just as naturally as they do to functions. A generic interface lets you define a reusable shape parameterized by a type, which is extremely common for things like API response wrappers or container types. A generic class lets you build reusable data structures, like a typed stack, queue, or cache, where the specific type of data it holds is decided by whoever instantiates the class. In both cases, the generic parameter is declared right after the interface or class name, and every member inside can reference that parameter.

Example
interface ApiResponse<T> {
  data: T;
  status: number;
  error?: string;
}

class Stack<T> {
  private items: T[] = [];
  push(item: T): void { this.items.push(item); }
  pop(): T | undefined { return this.items.pop(); }
}

const userResponse: ApiResponse<{ name: string }> = { data: { name: "Afnan" }, status: 200 };
const numberStack = new Stack<number>();

Follow-up Questions
How is a generic class different from a generic function in terms of when the type is bound?
Can a class have multiple generic type parameters?
Have you built a generic utility class or hook in a real project?

Common Mistakes
❌ Believing generics only apply to functions and forgetting their use in interfaces and classes.
❌ Not realizing a generic class's type parameter is bound once at instantiation, not per method call.

Interview Tips
Interview Tip:
The typed Stack example is a great one to have memorized, it's simple, realistic, and clearly demonstrates why a generic class is more useful than a hardcoded number[] or string[] stack.

Question 4
Can a generic function or type have multiple type parameters, and how do you use them together?

Answer
Yes, you can declare as many generic type parameters as you need, separated by commas inside the angle brackets. This is common for functions that combine two independent pieces of data with potentially different types, like a key-value pair, a merge function, or a mapping utility. Each parameter is independently inferred from wherever it's used in the function signature, and you can also constrain one type parameter based on another, which becomes especially powerful when working with object keys.

Example
function merge<T, U>(first: T, second: U): T & U {
  return { ...first, ...second };
}

const merged = merge({ name: "Afnan" }, { age: 28 });
// merged is typed as { name: string } & { age: number }

Follow-up Questions

❌ Not considering whether a simpler intersection or overload might be clearer than multiple generics.

Interview Tips
Interview Tip:

Question 5
What are default generic type parameters, and when would you use one?

Answer
Just like function parameters can have default values, generic type parameters can have a default type, specified with an equals sign after the parameter name. This means if the caller doesn't explicitly provide a type argument, and there's nothing to infer it from, TypeScript falls back to the specified default instead of resulting in an error or an implicit any. This is useful for generic utilities where there's a sensible, common default type, but you still want to allow full flexibility for callers who need something different.

Example
interface ApiResponse<T = unknown> {
  data: T;
  status: number;
}

function createResponse<T = Record<string, unknown>>(data: T): ApiResponse<T> {
  return { data, status: 200 };
}

const generic: ApiResponse = { data: "anything", status: 200 }; // T defaults to unknown

Follow-up Questions

Common Mistakes
❌ Defaulting a generic to any instead of a safer choice like unknown.
❌ Not realizing default generics reduce the need for verbose explicit type arguments in the common case.

Interview Tips
Interview Tip:
React's built-in types use default generics extensively, for instance useState's generic defaults based on the initial value passed in. Mentioning this ties the concept to something interviewers will immediately recognize.

TOPIC 25 - GENERIC CONSTRAINTS
====================================================

Question 1
What is a generic constraint, and why would you use one?

Answer
A generic constraint restricts what types are allowed to be passed for a generic parameter, using the extends keyword followed by the required shape or type. Without a constraint, a generic type parameter can be absolutely anything, which means TypeScript won't let you assume it has any particular properties or methods. A constraint tells the compiler "T can be anything, but it must at least have this shape," which then lets you safely access those specific properties or methods inside the function, while still preserving full type safety and flexibility for anything beyond that minimum shape.

Example
interface HasLength {
  length: number;
}

function logLength<T extends HasLength>(item: T): T {
  console.log(item.length); // safe, constraint guarantees a length property exists
  return item;
}

logLength("hello"); // valid, strings have length
logLength([1, 2, 3]); // valid, arrays have length
logLength(42); // error: number doesn't satisfy the HasLength constraint

Follow-up Questions
What happens if you try to access a property on an unconstrained generic type?
Can a generic constraint reference an interface, a type alias, or even another generic parameter?
How does this differ from just typing the parameter directly as HasLength without a generic at all?

Common Mistakes
❌ Trying to access a specific property on a completely unconstrained generic parameter.
❌ Not realizing a constraint still preserves the exact input type, unlike typing the parameter directly as the constraint's shape.

Interview Tips
Interview Tip:
Emphasize the difference between constraining T and just typing the parameter as HasLength directly, the generic constraint still returns the exact, specific input type, not the widened constraint type, this precision is the whole point.

----------------------------------------------------

Question 2
How can a generic type parameter be constrained using another generic type parameter?

Answer
This is a common pattern when you need one type parameter to represent a valid key of an object represented by another type parameter. You constrain the second type parameter with extends keyof FirstParameter, which means the second generic can only be one of the actual property names that exist on the first. This combination is exactly how a lot of safe, generic property-access utilities are built, guaranteeing at compile time that you can never request a key that doesn't actually exist on the object.

Example
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: "Afnan", age: 28 };
getProperty(user, "name"); // valid, returns string
getProperty(user, "email"); // error: '"email"' is not a valid key of the inferred type

Follow-up Questions
Why does K need to be constrained with keyof T specifically, rather than just string?
How does the return type T[K] work, and what is it called?
Where else have you seen this getProperty pattern used, like in libraries such as Lodash's typed get function?

Common Mistakes
❌ Constraining the key parameter as a plain string instead of keyof T, losing the compile-time key validation.
❌ Not recognizing T[K] as an indexed access type, and being unable to explain what it represents.

Interview Tips
Interview Tip:
This exact getProperty pattern is one of the most frequently asked "write this generic function" coding questions in TypeScript interviews. Have it memorized well enough to type from scratch under pressure.

Question 3
What does "extends" mean in the context of a generic constraint, and how is that different from interface extension?

Answer
The word extends is reused in TypeScript for two related but distinct purposes. In a generic constraint, T extends SomeType means "T must be assignable to, or compatible with, SomeType," essentially setting an upper bound on what T is allowed to be, it's a type-level relationship check, not an inheritance mechanism. This is conceptually different from interface extension, where extends literally builds a new interface by combining members from a parent interface. Both use the same keyword, but generic constraints are about compatibility and boundaries, while interface extension is about composition and inheritance of shape.

Example
// Generic constraint: T must be compatible with { id: string }
function findById<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find((item) => item.id === id);
}

// Interface extension: composing a new shape
interface BaseEntity { id: string; }
interface Product extends BaseEntity { price: number; }

Follow-up Questions
Why does TypeScript reuse the extends keyword for these two different purposes?
Is a generic constraint checking a subtype relationship or a structural compatibility?
Can a generic constraint use a union type as its bound?

Common Mistakes
❌ Conflating generic constraints with class or interface inheritance, they're conceptually different uses of the same keyword.
❌ Assuming a generic constraint requires an exact match rather than just structural compatibility.

Interview Tips
Interview Tip:
Clearly separate "compatibility check" from "composition mechanism" in your explanation, this distinction is exactly what a strong senior answer sounds like on this specific question.

TOPIC 26 - GENERICS GET PROP (KEYOF)
====================================================

Question 1
What does the keyof operator do, and how is it used with generics?

Answer
keyof takes an object type and produces a union of its property names as string literal types. It's a way to derive a type directly from the keys of another type, rather than manually writing out a union of literal strings that could easily drift out of sync as the object type changes. Combined with generics, keyof is the foundation for writing safe, reusable property-access utilities, since it lets you constrain a key parameter to only the actual valid keys of a given generic object type, which the compiler then enforces at every call site.

Example
interface Product {
  id: string;
  name: string;
  price: number;
}

type ProductKeys = keyof Product; // "id" | "name" | "price"

function pluck<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const result = {} as Pick<T, K>;
  keys.forEach((key) => { result[key] = obj[key]; });
  return result;
}

Follow-up Questions
How does keyof stay automatically in sync when the underlying object type changes?
What's the difference between keyof on an interface versus keyof on a type with an index signature?
How does keyof combine with indexed access types like T[K]?

Common Mistakes
❌ Manually writing out a union of key names instead of deriving it with keyof, causing drift over time.
❌ Forgetting that keyof on a type with a string index signature returns string | number, not a specific literal union.

Interview Tips
Interview Tip:
Emphasize the "stays in sync automatically" benefit, that's the actual reason keyof exists rather than just manually typing a union of key names, and it's what interviewers want to hear you articulate.

----------------------------------------------------

Question 2
What is an indexed access type, and how does it relate to keyof?

Answer
An indexed access type lets you look up the type of a specific property on another type, using bracket syntax, similar to how you'd access a property at runtime, but at the type level. Written as T[K], it evaluates to whatever type the property K actually has within T. This pairs extremely naturally with keyof, since keyof T gives you every valid key, and T[K] lets you retrieve the corresponding value type for any one of those keys, which together form the backbone of generic property-access functions like getProperty.

Example
interface Product {
  id: string;
  name: string;
  price: number;
}

type PriceType = Product["price"]; // number
type AnyValue = Product[keyof Product]; // string | number, union of all property value types

Follow-up Questions

Can indexed access types work with array types too, to get the element type?
How is T[K] used inside the return type of a generic getProperty function?

Common Mistakes
❌ Confusing indexed access type syntax, T["key"], with a runtime object property access.
❌ Not realizing you can index with keyof T itself to get a union of all possible value types.

Interview Tips
Interview Tip:
Show the trick of getting an array's element type with something like type Elem = MyArray[number], it's a small but impressive detail that goes beyond the basic getProperty pattern.

Question 3
Write a generic function called pluck that extracts a subset of properties from an object, given an array of keys.

Answer
This is a classic generic coding exercise that combines keyof, generic constraints, and the Pick utility type all in one function. The function takes an object of generic type T, and an array of keys constrained to keyof T, then returns a new object containing only those specified properties, typed precisely using Pick<T, K>. Internally, you build the result by iterating over the requested keys and copying each corresponding value from the source object, which requires a small type assertion since TypeScript can't fully verify the incrementally built object matches Pick<T, K> until every key has been added.

Example
function pluck<T extends object, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const result = {} as Pick<T, K>;
  for (const key of keys) {
    result[key] = obj[key];
  }
  return result;
}

const user = { id: "1", name: "Afnan", email: "afnan@example.com", age: 28 };
const publicUser = pluck(user, ["id", "name"]); // { id: string; name: string }

Follow-up Questions
Why is a type assertion needed on the initial empty result object?
How does this function's return type relate to the built-in Pick utility type?
How would you write the opposite function, omit, using a similar approach?

Common Mistakes
❌ Typing the keys parameter as a plain string[] instead of K[] constrained to keyof T, losing key safety.
❌ Forgetting the type assertion on the initial result object, which causes a compiler error while building it incrementally.

Interview Tips
Interview Tip:
This is one of the single most common "write this from scratch" TypeScript interview questions. Practice writing it without looking it up until it's fully memorized.

TOPIC 27 - UTILITY TYPES
====================================================

Question 1
What are utility types in TypeScript, and can you name the most commonly used ones?

Answer
Utility types are built-in generic types that TypeScript ships with to perform common type transformations, so you don't have to write the same mapped or conditional type logic from scratch every time. The most commonly used ones include Partial, which makes every property optional, Required, which makes every property mandatory, Readonly, which makes every property immutable at the type level, Pick, which selects a subset of properties, Omit, which excludes a subset of properties, and Record, which builds an object type from a set of keys and a value type. I use these constantly, especially Partial and Pick, when modeling update payloads or narrowing down a larger interface for a specific use case.

Example
interface User {
  id: string;
  name: string;
  email: string;
  isAdmin: boolean;
}

type UserUpdate = Partial<User>; // every property optional, for PATCH requests
type PublicUser = Omit<User, "email">; // everything except email
type UserSummary = Pick<User, "id" | "name">; // only id and name

Follow-up Questions
How is Partial implemented internally using a mapped type?
What's the difference between Omit and Pick, conceptually?
Where have you used Partial in a real-world scenario, like an update API?

Common Mistakes
❌ Manually rewriting a whole new interface instead of deriving it from an existing one with a utility type.
❌ Not knowing these utility types are just built-in mapped or conditional types, not special compiler magic.

Interview Tips
Interview Tip:
Mention the PATCH-endpoint use case for Partial specifically, it's the most relatable, common real-world justification for that utility type and shows practical API design awareness.

Question 2
How would you implement your own version of the Partial utility type from scratch?

Answer
Partial is implemented as a mapped type, which iterates over every key in a given type and adds a question mark to make each property optional, while preserving each property's original type. Understanding how to build it from scratch demonstrates you know mapped types aren't magic, they're just syntax for transforming one object type into another by looping over its keys.

Example
type MyPartial<T> = {
  [P in keyof T]?: T[P];
};

interface User { id: string; name: string; }
type PartialUser = MyPartial<User>; // { id?: string; name?: string }

Follow-up Questions
How would you implement Required, the opposite of Partial, from scratch?
What does the "in" keyword do inside a mapped type?
How would you implement Readonly using the same mapped type pattern?

Common Mistakes
❌ Believing Partial, Required, and Readonly are special compiler built-ins rather than simple mapped types.
❌ Forgetting the question mark placement, after the mapped key, not before the type.

Interview Tips
Interview Tip:
Being able to write MyPartial, MyRequired, and MyReadonly from memory in under a minute is a great way to demonstrate real fluency with mapped types during a live coding portion of an interview.

Question 3
What is the difference between Pick and Omit, and how would you implement Omit using Pick and Exclude?

Answer
Pick selects a specific subset of properties from a type, given a union of key names you want to keep. Omit does the opposite conceptually, it removes a specific subset of properties, given a union of key names you want to exclude, keeping everything else. Internally, Omit is actually implemented in terms of Pick and Exclude together: it takes all the keys of the original type, excludes the ones you specified using Exclude, and then Picks only the remaining keys, which is a nice example of how TypeScript's utility types are often composed from smaller, more primitive pieces.

Example
type MyOmit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;

interface User { id: string; name: string; email: string; }
type UserWithoutEmail = MyOmit<User, "email">; // { id: string; name: string }

Follow-up Questions
What does Exclude actually do on its own?
Why is the constraint on K written as "keyof any" rather than "keyof T" in Omit's real definition?
Can you Pick or Omit using a single key instead of a union of keys?

Common Mistakes
❌ Thinking Omit and Pick are entirely separate, unrelated implementations rather than Omit being built from Pick.
❌ Not knowing what Exclude does when asked to break down Omit's internals.

Interview Tips
Interview Tip:
Walking through Omit's actual internal definition, Pick plus Exclude, is a fantastic way to show depth beyond just "knowing how to use" utility types, it shows you understand how they're built.

TOPIC 28 - FUNCTION UTILITY TYPES
====================================================

Question 1
What do the Parameters and ReturnType utility types do?

Answer
Parameters<T> takes a function type and extracts a tuple representing all of its parameter types, in order. ReturnType<T> takes a function type and extracts whatever type it returns. Both are extremely useful when you want to derive a type from an existing function rather than manually re-typing its signature elsewhere, which keeps everything in sync automatically if the original function's signature ever changes. These are especially handy when working with third-party functions where you don't control the source but still want to reuse their exact parameter or return types elsewhere in your code.

Example
function createUser(name: string, age: number) {
  return { id: crypto.randomUUID(), name, age };
}

type CreateUserParams = Parameters<typeof createUser>; // [name: string, age: number]
type CreateUserReturn = ReturnType<typeof createUser>; // { id: string; name: string; age: number }

Follow-up Questions

How would you extract just the first parameter's type from a function?
Where have you used ReturnType to avoid manually duplicating a type?

Common Mistakes
❌ Forgetting the typeof keyword when passing an actual function value instead of a type into Parameters or ReturnType.
❌ Manually duplicating a function's return shape as a separate interface instead of deriving it with ReturnType.

Interview Tips
Interview Tip:
Point out that typeof is required because Parameters and ReturnType operate on types, not values, so you must first convert the function value into its type using typeof before extracting from it.

----------------------------------------------------

Question 2
What is the InstanceType utility type, and when would you use it?

Answer
InstanceType<T> takes the type of a class, meaning its constructor function type, and extracts the type of the instances that class produces. This is useful when you're working with a class dynamically, for example receiving a class reference as a parameter rather than an already-created instance, and you need to describe the type of objects that class will eventually construct, without manually re-declaring that shape separately.

Example
class ApiClient {
  constructor(public baseUrl: string) {}
  get(path: string) { return fetch(this.baseUrl + path); }
}

type ApiClientInstance = InstanceType<typeof ApiClient>; // same as an actual ApiClient instance's shape

function createInstance<T extends new (...args: any[]) => any>(ClassRef: T): InstanceType<T> {
  return new ClassRef();
}

Follow-up Questions
Why is typeof needed here as well, similar to Parameters and ReturnType?
How does InstanceType relate to a constructor function type signature?
Where might you use InstanceType in a factory function or dependency injection setup?

Common Mistakes
❌ Confusing InstanceType, which extracts an instance shape, with ReturnType, which extracts a function's return value.
❌ Not knowing how to write the "new (...args: any[]) => any" constructor type signature when needed.

Interview Tips
Interview Tip:
InstanceType is less commonly used day-to-day than Parameters or ReturnType, so if it comes up, calmly walking through the constructor-type signature shows solid, unshaken understanding of advanced generics.

Question 3
How would you type a higher-order function that wraps another function while preserving its exact parameter and return types?

Answer
This is a great real-world combination of generics with Parameters and ReturnType. You make the higher-order function generic over the type of the function being wrapped, constrained to any function shape, and then use Parameters and ReturnType on that generic to describe the wrapped function's own signature precisely, ensuring the wrapper is fully type-safe and automatically adapts to whatever function is passed in, without needing separate overloads for every possible signature.

Example
function withLogging<T extends (...args: any[]) => any>(fn: T) {
  return (...args: Parameters<T>): ReturnType<T> => {
    console.log("Calling with args:", args);
    return fn(...args);
  };
}

function add(a: number, b: number): number { return a + b; }
const loggedAdd = withLogging(add);
loggedAdd(2, 3); // fully typed: args are [number, number], return is number

Follow-up Questions
Why is the generic constrained to "(...args: any[]) => any" instead of something narrower?
How does this pattern show up in real-world middleware or decorator implementations?
Would this approach work for wrapping an async function as well?

Common Mistakes
❌ Manually re-typing the wrapped function's parameters and return type instead of deriving them generically.
❌ Using any instead of Parameters<T> and ReturnType<T>, which loses type safety for the wrapper entirely.

Interview Tips
Interview Tip:
This pattern is exactly how real logging middleware, decorators, and memoization utilities are typed in production codebases. Mentioning that connection elevates the answer beyond a purely academic exercise.

TOPIC 29 - UNION HELPERS
====================================================

Question 1
What do the Exclude and Extract utility types do, and how are they different?

Answer
Both operate on union types, but they do opposite things. Exclude<T, U> takes a union T and removes any members that are assignable to U, leaving only what doesn't match. Extract<T, U> does the reverse, it keeps only the members of T that are assignable to U, discarding everything else. I think of Exclude as "give me everything except this" and Extract as "give me only this," applied to a union of types rather than a single value.

Example
type Status = "pending" | "active" | "completed" | "cancelled";

type ActiveStatus = Exclude<Status, "cancelled" | "completed">; // "pending" | "active"
type FinishedStatus = Extract<Status, "completed" | "cancelled">; // "completed" | "cancelled"

Follow-up Questions
How are Exclude and Extract implemented internally using conditional types?
Can Exclude and Extract operate on unions of object types, not just string literals?
How does Omit rely on Exclude internally?

Common Mistakes
❌ Mixing up which one keeps versus removes, Exclude removes matches, Extract keeps matches.
❌ Assuming these only work on string literal unions, they work on any union type, including objects.

Interview Tips
Interview Tip:
Use the mnemonic "Exclude excludes, Extract extracts" out loud during the interview, it's a small verbal trick that helps you avoid mixing them up under pressure.

----------------------------------------------------

Question 2
What does the NonNullable utility type do, and when would you use it?

Answer
NonNullable<T> takes a type and removes null and undefined from it, leaving whatever's left. It's essentially a specialized version of Exclude, purpose-built for the extremely common case of stripping nullability out of a type after you've already handled or guaranteed the value can't be null or undefined at that point in your code, for example after a validation step or a filter operation on an array.

Example
type MaybeUser = { name: string } | null | undefined;
type DefiniteUser = NonNullable<MaybeUser>; // { name: string }

const users: (string | null)[] = ["Afnan", null, "Sara"];
const definiteUsers: string[] = users.filter((u): u is NonNullable<typeof u> => u !== null);

Follow-up Questions
How is NonNullable implemented in terms of Exclude?
How does NonNullable interact with a filter callback using a type predicate?
Where have you used NonNullable in a real codebase, maybe after filtering an array?

Common Mistakes
❌ Manually writing Exclude<T, null | undefined> instead of just using the more direct, purpose-built NonNullable.
❌ Forgetting that filtering out nulls at runtime still requires a type predicate for TypeScript to actually narrow the resulting array's type.

Interview Tips
Interview Tip:
The filter-with-type-predicate example ties this back to the earlier array narrowing topic, showing connected knowledge across the type system rather than isolated facts.

----------------------------------------------------

Question 3
How would you implement Exclude from scratch using a conditional type?

Answer
Exclude relies on a distributive conditional type, which is a conditional type that automatically applies itself individually across every member of a union, rather than treating the union as one single value. For each member of the union T, it checks whether that specific member is assignable to U; if it is, it resolves to never for that member, which effectively removes it from the resulting union, since never members disappear when a union is built back up. If it's not assignable to U, the member is kept as-is.

Example
type MyExclude<T, U> = T extends U ? never : T;

type Status = "pending" | "active" | "cancelled";
type NotCancelled = MyExclude<Status, "cancelled">; // "pending" | "active"

Follow-up Questions
What makes this a "distributive" conditional type specifically?
What would happen if T were wrapped in a tuple, like [T], instead of used directly?
How would you implement Extract using the opposite logic?

Common Mistakes
❌ Not recognizing that the distributive behavior only happens because T is a naked type parameter directly in the conditional.
❌ Struggling to explain why never members effectively vanish from a resulting union.

Interview Tips
Interview Tip:
This question often leads directly into distributive conditional types as a broader topic, be ready to explain that wrapping T in a tuple, like [T] extends [U], disables the distributive behavior, since that's a very common, more advanced follow-up.

TOPIC 30 - AWAITED UTILITY & PROMISES
====================================================

Question 1
What does the Awaited utility type do, and why was it added to TypeScript?

Answer
Awaited<T> recursively unwraps a Promise type to get the type of the value it eventually resolves to, including cases where a Promise resolves to another Promise, which does happen with certain async patterns and needed proper, deep unwrapping rather than stopping after just one level. It was added specifically to correctly model the return type of async functions and to fix inaccuracies in how TypeScript handled chained or nested promises before Awaited existed as a dedicated utility. I mainly use it when I need to describe "the type this promise eventually gives me" in a generic utility, without manually writing out repetitive Promise-unwrapping logic myself.

Example
async function getUser(): Promise<{ name: string }> {
  return { name: "Afnan" };
}

type UserResult = Awaited<ReturnType<typeof getUser>>; // { name: string }, not Promise<{ name: string }>

type Nested = Promise<Promise<number>>;
type Resolved = Awaited<Nested>; // number, fully unwrapped, not Promise<number>

Follow-up Questions
Why does Awaited need to handle nested Promises specifically?
How does Awaited combine with ReturnType to get the resolved value of an async function?
Was there a way to achieve this before Awaited was introduced?

Common Mistakes
❌ Assuming a single level of unwrapping is always enough, missing genuinely nested Promise cases.
❌ Not knowing Awaited combines naturally with ReturnType for async function result types.

Interview Tips
Interview Tip:

Question 2
How do you properly type a function that returns different Promise types depending on a condition?

Answer
Just like a synchronous function can have a union return type across multiple return statements, an async function can too, and TypeScript will infer the resolved value as a union across all the possible resolved types, still wrapped in a single Promise. You annotate this explicitly as Promise<TypeA | TypeB> if you want to be clear about the contract, rather than relying purely on inference, especially for exported async functions.

Example
async function fetchResource(type: "user" | "post"): Promise<{ name: string } | { title: string }> {
  if (type === "user") {
    return { name: "Afnan" };
  }
  return { title: "My Blog Post" };
}

const result = await fetchResource("user");
if ("name" in result) {
  console.log(result.name); // narrowed correctly after await
}

Common Mistakes

Question 3
How does TypeScript type Promise.all, and what does the resulting array's type look like?

Answer
Promise.all takes an array or tuple of promises and returns a single promise that resolves once every input promise has resolved, with the resolved value being an array or tuple of each individual resolved value, in the same order. TypeScript is smart enough to infer this correctly even when the input promises resolve to different types, producing a properly typed tuple rather than a generic union array, as long as you pass the promises as a tuple literal rather than a loosely typed array.

Example
async function loadDashboardData() {
  const [user, posts, settings] = await Promise.all([
    fetchUser(),      // Promise<User>
    fetchPosts(),      // Promise<Post[]>
    fetchSettings(),   // Promise<Settings>
  ]);
  // user: User, posts: Post[], settings: Settings, each correctly and individually typed
}

async function fetchUser(): Promise<{ name: string }> { return { name: "Afnan" }; }
async function fetchPosts(): Promise<{ title: string }[]> { return []; }
async function fetchSettings(): Promise<{ theme: string }> { return { theme: "dark" }; }

Follow-up Questions
What happens to the resulting type if one of the promises in Promise.all rejects?
How is Promise.all different from Promise.allSettled in both behavior and typing?
Would this tuple-preserving inference still work if the array were stored in a variable first?

Common Mistakes
❌ Assuming Promise.all always collapses to a single union type array instead of preserving individual positional types.
❌ Not knowing that storing the array in an intermediate loosely typed variable first can widen the tuple into a less precise array type.

Interview Tips
Interview Tip:
Mention Promise.allSettled as a natural follow-up comparison, it resolves even if some promises reject, and its resulting type wraps each entry in a status-tagged object instead, which is a good contrast to bring up proactively.

TOPIC 31 - CLASSES & CONSTRUCTORS
====================================================

Question 1
How does TypeScript enhance JavaScript classes with type safety?

Answer
TypeScript adds type annotations to class properties, constructor parameters, and method signatures, so the compiler can catch mismatches involving class instances the same way it does for plain objects and functions. It also adds features JavaScript classes alone don't have, like access modifiers for encapsulation, abstract classes and methods, readonly properties, and parameter properties, which is a shorthand for declaring and assigning a class property directly from a constructor parameter. All of this exists purely at compile time; the actual JavaScript output for a class is essentially standard ES6 class syntax with the type annotations stripped away.

Example
class BankAccount {
  private balance: number;
  readonly accountId: string;

  constructor(accountId: string, initialBalance: number = 0) {
    this.accountId = accountId;
    this.balance = initialBalance;
  }

  deposit(amount: number): void {
    this.balance += amount;
  }

  getBalance(): number {
    return this.balance;
  }
}

Follow-up Questions
What class features does TypeScript add that plain JavaScript classes lack?
Do class type annotations have any effect on runtime behavior?
How does TypeScript enforce that a class properly implements an interface?

Common Mistakes
❌ Assuming private and other access modifiers provide genuine runtime protection, they're compile-time only unless using the newer JavaScript native # private fields.
❌ Forgetting that class type annotations disappear entirely after compilation.

Interview Tips
Interview Tip:
Bring up the distinction between TypeScript's private keyword and JavaScript's native #privateField syntax, this is a well-known nuance that shows awareness of the evolving language.

Question 2
How would you use a class to implement a specific interface, and what does that guarantee?

Answer
A class uses the implements keyword to declare that it must satisfy a given interface's contract, meaning every property and method defined in the interface has to be present on the class with a compatible type, or the compiler throws an error. This is purely a compile-time contract check, implements doesn't affect the class's prototype chain or runtime behavior at all, unlike extends, which does establish real inheritance. It's commonly used to guarantee multiple unrelated classes all conform to the same shape, without forcing them into a shared inheritance hierarchy.

Example
interface Serializable {
  serialize(): string;
}

class Product implements Serializable {
  constructor(private name: string, private price: number) {}
  serialize(): string {
    return JSON.stringify({ name: this.name, price: this.price });
  }
}

Follow-up Questions
Does implementing an interface affect a class's prototype chain at runtime?
Can a class implement multiple interfaces at once?
What happens if a class fails to implement one of the interface's required members?

Common Mistakes
❌ Confusing implements, a contract check, with extends, actual inheritance with shared runtime behavior.
❌ Forgetting a class can implement several interfaces simultaneously, separated by commas.

Interview Tips
Interview Tip:
State plainly that implements is a compile-time-only contract with zero runtime footprint, this distinction from extends is a frequently asked, easy-to-get-wrong detail.

Question 3
What is the difference between a class's static members and its instance members?

Answer
Instance members, both properties and methods, belong to each individual object created from the class, every instance gets its own copy of instance properties and shares the class's methods through the prototype chain. Static members belong to the class itself, not to any individual instance, they're accessed directly through the class name and exist only once, shared across the entire class regardless of how many instances are created. I use static members for utility functions related to a class that don't need any particular instance's state, like a factory method, or for shared configuration or counters across every instance.

Example
class User {
  static count = 0; // shared across all instances

  constructor(public name: string) {
    User.count++; // increments the shared static counter
  }

  static createGuest(): User {
    return new User("Guest");
  }
}

new User("Afnan");
new User("Sara");
console.log(User.count); // 2

Follow-up Questions
Can a static method access instance properties directly?
Why would you use a static factory method instead of just calling the constructor directly?
How does TypeScript type a static property versus an instance property differently?

Common Mistakes
❌ Trying to access "this" referring to an instance inside a static method, static methods aren't bound to any particular instance.
❌ Confusing static properties, which are shared, with instance properties, which each object owns independently.

Interview Tips
Interview Tip:
The static factory method pattern, like createGuest, is a great real-world example to mention, it shows understanding beyond just "static counters," connecting to actual object-oriented design patterns.

TOPIC 32 - ACCESS MODIFIERS (PRIVATE/PUBLIC)
====================================================

Question 1
What do the public and private access modifiers do in a TypeScript class?

Answer
public is the default visibility for every class member if you don't specify anything, meaning the property or method can be accessed from anywhere, inside the class, from subclasses, and from outside code entirely. private restricts access to only within the exact class where it's declared, not even subclasses can access a private member directly. This is a compile-time-only restriction that TypeScript's type checker enforces; it doesn't produce any actual runtime protection in the compiled JavaScript output unless you use the newer, genuinely runtime-private # syntax that's part of JavaScript itself rather than TypeScript's own private keyword.

Example
class Account {
  public accountId: string;
  private balance: number;

  constructor(accountId: string, balance: number) {
    this.accountId = accountId;
    this.balance = balance;
  }

  private logTransaction(amount: number) {
    console.log(`Transaction of ${amount}`);
  }
}

const account = new Account("123", 500);
console.log(account.accountId); // fine, public
console.log(account.balance); // error: 'balance' is private and only accessible within class 'Account'

Follow-up Questions
Does TypeScript's private keyword prevent access at runtime, or only at compile time?
How is TypeScript's private different from JavaScript's native #privateField?
Can a subclass access a private member of its parent class?

Common Mistakes
❌ Assuming TypeScript's private keyword provides genuine runtime encapsulation.
❌ Forgetting that a subclass cannot access a parent class's private members, only protected ones.

Interview Tips
Interview Tip:
Explicitly state that TypeScript's private is erased at compile time and provides zero runtime protection, someone could still access the property from plain JavaScript, this is a very commonly tested nuance.

----------------------------------------------------

Question 2
What is the difference between TypeScript's private keyword and JavaScript's native #privateField syntax?

Answer
TypeScript's private keyword is purely a compile-time construct, it exists only in the type system, and after compilation, the property becomes a completely normal, publicly accessible JavaScript property, just with a different name convention at most. JavaScript's native private fields, written with a hash prefix, are enforced by the JavaScript engine itself at runtime, meaning code outside the class genuinely cannot access or even detect the existence of that field, not even through reflection tricks like Object.keys or bracket notation. If real runtime privacy actually matters, for example in a library where you don't trust consumers not to reach into internals, native # private fields are the correct choice, not TypeScript's private keyword.

Example
class TypeScriptPrivate {
  private secret = "hidden by TypeScript only";
}
// After compilation, "secret" is a completely normal, accessible property

class NativePrivate {
  #secret = "hidden by the JavaScript engine itself";
  reveal() { return this.#secret; }
}

const instance = new NativePrivate();
console.log(instance.reveal()); // works
// console.log(instance.#secret); // syntax error, genuinely inaccessible from outside

Follow-up Questions
Why would a library author choose native #privateField over TypeScript's private keyword?
Does native # private syntax work in all JavaScript environments and browser versions?
How does this distinction relate to writing genuinely secure or tamper-resistant code?

Common Mistakes
❌ Assuming TypeScript's private and JavaScript's #privateField behave identically, they don't, one is enforced by the compiler only, the other by the runtime engine.
❌ Not knowing native private fields have their own browser and Node.js compatibility considerations for older environments.

Interview Tips
Interview Tip:
This is a favorite senior-level question precisely because so many developers use TypeScript's private keyword without ever realizing it offers no real protection. Answering this confidently is a strong signal.

Question 3
What is a parameter property, and how does it simplify constructor code?

Answer
A parameter property is a shorthand where you add an access modifier, public, private, protected, or readonly, directly in front of a constructor parameter, and TypeScript automatically both declares that property on the class and assigns it from the parameter, without you needing to write a separate property declaration and a separate this.propertyName = propertyName assignment line. This significantly reduces boilerplate for classes with several straightforward properties that just get set directly from the constructor arguments.

Example
// Without parameter properties
class UserVerbose {
  public name: string;
  private age: number;
  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
  }
}

// With parameter properties, much more concise
class UserConcise {
  constructor(public name: string, private age: number) {}
}

TOPIC 33 - ACCESS MODIFIERS (PROTECTED)
====================================================

Question 1
What does the protected access modifier do, and how is it different from private?

Answer
protected behaves like private in that it prevents access from outside the class entirely, but it differs in one important way: subclasses can access protected members of their parent class, whereas they cannot access private members at all. This makes protected the right choice for internal implementation details that should still be usable by any class extending the base class, essentially designed specifically for inheritance hierarchies, while private is meant for details that should stay fully encapsulated within a single class, with no exceptions even for subclasses.

Example
class Animal {
  protected sound: string = "generic sound";
  protected makeSound(): void {
    console.log(this.sound);
  }
}

class Dog extends Animal {
  bark(): void {
    this.sound = "Woof"; // valid, protected accessible from subclass
    this.makeSound();
  }
}

new Dog().makeSound(); // error: 'makeSound' is protected and only accessible within class 'Animal' and its subclasses

Follow-up Questions
Why would you choose protected over private when designing a base class meant to be extended?
Can code outside the class hierarchy ever access a protected member?
How does protected affect constructors specifically?

Common Mistakes
❌ Using private for members that subclasses genuinely need to access, forcing awkward workarounds.
❌ Assuming protected allows access from anywhere, it still blocks access from completely unrelated, external code.

Interview Tips
Interview Tip:
Frame protected as "private, but inheritance-friendly," that's a clean, memorable way to summarize the distinction quickly and accurately.

----------------------------------------------------

Question 2
What does a protected constructor do, and why would you use one?

Answer
Marking a class's constructor itself as protected prevents that class from being instantiated directly with the "new" keyword from outside code, while still allowing subclasses to call it internally through super() in their own constructors. This is a common pattern for enforcing that a base class should only ever be used through a specific subclass, or through a controlled factory method, rather than being instantiated on its own, which is especially useful for abstract-like base classes or singleton patterns.

Example
class Singleton {
  private static instance: Singleton;
  protected constructor() {}

  static getInstance(): Singleton {
    if (!Singleton.instance) {
      Singleton.instance = new Singleton();
    }
    return Singleton.instance;
  }
}

const instance = new Singleton(); // error: constructor is protected
const singleton = Singleton.getInstance(); // valid, controlled instantiation

Follow-up Questions
How does a protected constructor differ from a private constructor?
Why is this pattern common for implementing a Singleton?
What is an abstract class, and how does it relate to preventing direct instantiation?

Common Mistakes
❌ Confusing protected constructors, which still allow subclass instantiation, with private constructors, which don't even allow that.
❌ Not connecting this pattern to well-known design patterns like Singleton or Factory.

Interview Tips
Interview Tip:

Question 3
Can a protected member be accessed by a sibling subclass, meaning another subclass of the same base class, rather than a direct instance?

Answer
This is a subtle rule. A protected member is accessible within the class hierarchy, but specifically only through the type of the instance calling it relative to the class where the access happens, not simply because two classes happen to share a common ancestor. In practice, one subclass generally cannot reach into a protected member of a different, unrelated instance of a sibling subclass unless that access happens through a properly typed reference within the shared hierarchy, this specific rule trips up even experienced developers and depends on exact context.

Example
class Animal {
  protected age: number = 0;
}

class Dog extends Animal {
  compareAge(other: Dog): boolean {
    return this.age > other.age; // valid, 'other' is specifically typed as Dog, same subclass
  }
}

class Cat extends Animal {
  compareWithDog(dog: Dog): boolean {
    return this.age > dog.age; // error in some contexts: accessing protected member through a sibling class reference can be restricted
  }
}

TOPIC 34 - GETTERS & SETTERS
====================================================

Question 1
What are getters and setters in a TypeScript class, and why would you use them instead of a plain public property?

Answer
Getters and setters, declared with the get and set keywords, let you define custom logic that runs whenever a property is read or written, while still letting consumers of the class interact with it using normal property syntax rather than explicit method calls. This is useful for adding validation on write, computing a derived value on read, or controlling access without breaking the simple, intuitive dot-notation API consumers expect. I reach for them whenever a plain property needs some kind of guard or transformation, without wanting to force every caller to switch to explicit getValue or setValue method calls.

Example
class Temperature {
  private _celsius: number = 0;

  get celsius(): number {
    return this._celsius;
  }

  set celsius(value: number) {
    if (value < -273.15) {
      throw new Error("Temperature below absolute zero");
    }
    this._celsius = value;
  }

  get fahrenheit(): number {
    return this._celsius * 9 / 5 + 32;
  }
}

const temp = new Temperature();
temp.celsius = 25; // calls the setter, runs validation
console.log(temp.fahrenheit); // calls the getter, computes a derived value

Follow-up Questions

Do getters and setters have any runtime performance cost compared to a plain property?

Common Mistakes
❌ Overusing getters and setters for trivial properties with no actual logic, adding unnecessary indirection.
❌ Forgetting a getter-only property effectively becomes read-only from the outside, which is actually a useful, intentional pattern.

Interview Tips
Interview Tip:
The Fahrenheit-from-Celsius example is a great way to demonstrate a computed, derived getter, not just a validating setter, showing both directions of the pattern in one clean example.

Question 2
How would you use a getter to create a read-only computed property on a class?

Answer
By defining only a get accessor without a matching set accessor, you create a property that can be read from outside the class using normal dot syntax, but cannot be assigned to at all, TypeScript will throw a compile error on any attempted assignment. This is a clean way to expose a derived, calculated value, based on other private state, as if it were a simple, safe, read-only property, without exposing the underlying private data directly or requiring an explicit method call syntax.

Example
class Rectangle {
  constructor(private width: number, private height: number) {}

  get area(): number {
    return this.width * this.height;
  }
}

const rect = new Rectangle(4, 5);
console.log(rect.area); // 20, reads like a plain property
rect.area = 100; // error: cannot assign to 'area' because it only has a getter

Question 3
Can getters and setters have different types for reading versus writing the same property?

Answer
As of more recent TypeScript versions, yes, a getter and its corresponding setter are allowed to use different types, the getter's return type doesn't have to exactly match the setter's parameter type, as long as the setter's parameter type is assignable in a way that makes sense for the use case. This is useful for a property that accepts a looser, more flexible input type when being set, but always exposes a stricter, more specific, normalized type when read back out.

class StyleValue {
  private _value: number = 0;

  get value(): number {
    return this._value;

  set value(input: number | string) {
    this._value = typeof input === "string" ? parseFloat(input) : input;
  }
}

const style = new StyleValue();
style.value = "42.5"; // setter accepts a string
console.log(style.value); // getter always returns a number

TOPIC 35 - IMPORT & EXPORT
====================================================

Question 1
What is the difference between a named export and a default export in TypeScript, and which do you prefer?

Answer
A named export exports a specific, named binding from a module, and consumers must import it using that exact name, wrapped in curly braces, though they can rename it locally with an "as" clause if needed. A default export exports a single, primary value from a module, and consumers can import it under whatever name they choose, without curly braces. I generally prefer named exports for most modules, because they make refactoring safer, an editor can reliably rename every usage across a codebase, while default exports allow every importing file to use a different, inconsistent name for the same thing, which can hurt searchability and refactoring tooling.

Example
// utils.ts
export function formatCurrency(amount: number): string {
  return `$${amount.toFixed(2)}`;
}
export const TAX_RATE = 0.08;

// consumer.ts
import { formatCurrency, TAX_RATE } from "./utils";

// alternative default export style
export default class ApiClient {}
// consumer.ts
import MyClient from "./api-client"; // any name works, no curly braces

Follow-up Questions

Can a single module have both a default export and multiple named exports at once?
Is there a meaningful build-size or tree-shaking difference between the two?

Common Mistakes
❌ Renaming a default-exported class or function inconsistently across many files without noticing, since nothing enforces consistency.
❌ Assuming you can only have one export style per file, a module can mix both default and named exports.

Interview Tips
Interview Tip:
Have a clear, opinionated preference ready with a concrete reason, refactoring safety is a strong, defensible justification that goes beyond just personal taste.

Question 2
What is the difference between "import type" and a regular "import" statement in TypeScript?

Answer
A regular import statement can bring in both values, like functions, classes, and variables, and types, like interfaces and type aliases, from another module. The "import type" syntax explicitly signals that you're only importing something for type-checking purposes, never as an actual runtime value, and TypeScript guarantees that import gets completely erased during compilation, leaving zero trace in the emitted JavaScript. This distinction matters for build tools that process files in isolation, without full type information, since it helps them know for certain which imports are safe to strip out entirely without needing to resolve the whole module graph first.

Example
import type { User } from "./types"; // guaranteed erased, purely for type-checking
import { createUser } from "./userService"; // a real runtime import, will exist in the compiled output

function greet(user: User): string {
  return `Hello, ${user.name}`;
}

Follow-up Questions

Common Mistakes

❌ Forgetting that single-file transpilers, unlike tsc, can't always tell whether an import is type-only without this explicit hint.

Interview Tips
Interview Tip:

Question 3
What does "export *" do, and what is the difference between re-exporting and importing then exporting again manually?

Answer
"export * from './module'" re-exports every named export from another module, without you needing to import each one individually and re-export it by name, which is a convenient way to build an aggregating "barrel" file, a single entry point module that gathers and re-exports functionality from several smaller modules. This is functionally different from manually importing everything and then exporting it again, mainly in conciseness, though "export *" does not automatically re-export a default export, that needs to be handled separately, either with a named re-export syntax or by explicitly re-exporting it under a chosen name.

Example
// mathUtils.ts
export function add(a: number, b: number) { return a + b; }
export function subtract(a: number, b: number) { return a - b; }

// index.ts, a "barrel" file
export * from "./mathUtils";
export * from "./stringUtils";

// consumer.ts
import { add, subtract } from "./index";

Common Mistakes

TOPIC 36 - UNKNOWN TYPE (DEEP DIVE)
====================================================

Question 1
Why was the unknown type introduced when any already existed? What specific problem does it solve?

Answer
any existed from TypeScript's earliest versions as a full escape hatch, but that created a real gap: there was no proper way to say "this value could be anything, but I still want type safety enforced before I use it." unknown was introduced to fill exactly that gap. It accepts any value being assigned to it, just like any, but it refuses to let you perform any operation on that value, calling methods, accessing properties, using it in arithmetic, until you've actually narrowed it down through a proper type check. This makes unknown the correct default for genuinely uncertain data, like third-party input, while any remains reserved for situations where you deliberately want to fully opt out of type checking.

Example
function parseConfig(input: unknown): { debug: boolean } {
  if (
    typeof input === "object" &&
    input !== null &&
    "debug" in input &&
    typeof (input as any).debug === "boolean"
  ) {
    return { debug: (input as { debug: boolean }).debug };
  }
  throw new Error("Invalid config");
}

Follow-up Questions
What operations does TypeScript allow directly on an unknown value without narrowing?
Why is unknown described as a "type-safe any"?
How would a linting rule enforce unknown over any across a codebase?

Common Mistakes
❌ Treating unknown as just a slightly stricter version of any that can still be used loosely.
❌ Forgetting that even basic property access requires narrowing first when working with unknown.

Interview Tips
Interview Tip:
Describe unknown as "any, but the compiler still makes you prove what it is before you touch it." That phrasing captures the design intent precisely and memorably.

----------------------------------------------------

Question 2
How does unknown behave differently from any when it's part of a union or intersection type?

Answer
unknown has an absorbing effect in both unions and intersections, but in opposite directions. In a union, unknown absorbs everything else, meaning T | unknown always simplifies down to just unknown, since unknown already represents every possible value. In an intersection, unknown is absorbed by anything more specific, meaning T & unknown simplifies down to just T, since intersecting with "could be anything" doesn't add any additional restriction beyond what T already specifies. any behaves similarly in unions but is generally considered to "infect" whatever it touches in ways that are less predictable and more dangerous, since it doesn't just widen, it disables checking entirely for anything it comes into contact with.

Example
type WithUnion = string | unknown; // simplifies to unknown
type WithIntersection = string & unknown; // simplifies to string

type AnyUnion = string | any; // simplifies to any, and 'any' spreads through the union
type StillAny = AnyUnion extends string ? "yes" : "no"; // behaves unpredictably because of 'any'

Follow-up Questions
Why is any described as "infectious" in a way unknown is not?
Would you ever intentionally intersect a type with unknown? Why might that happen accidentally?
How does this absorbing behavior relate to unknown being considered the "top type"?

Common Mistakes
❌ Assuming any and unknown behave identically inside unions and intersections.
❌ Not recognizing unknown as TypeScript's "top type," the type that everything is assignable to.

Interview Tips
Interview Tip:
Referring to unknown as the "top type" of TypeScript's type system, and never as the "bottom type" which is what never actually is, shows precise, correct terminology that stands out in a technical discussion.

----------------------------------------------------

Question 3
How would you safely convert an unknown value into a specific, usable type in a production application?

Answer
The safest approach is to never trust a manual type assertion on genuinely unknown, external data, and instead use either a series of proper runtime checks combined with a custom type predicate, or, more robustly, a schema validation library like Zod that both validates the shape at runtime and derives the correct TypeScript type automatically from that same schema, keeping validation logic and type definitions permanently in sync rather than risking them drifting apart over time.

Example
function isUser(value: unknown): value is { id: string; name: string } {
  return (
    typeof value === "object" &&
    value !== null &&
    "id" in value &&
    "name" in value &&
    typeof (value as any).id === "string" &&
    typeof (value as any).name === "string"
  );
}

function handleApiResponse(response: unknown) {
  if (isUser(response)) {
    console.log(response.name); // safely narrowed
  } else {
    throw new Error("Unexpected response shape");
  }
}

Follow-up Questions
Why is a schema validation library generally preferred over hand-written type predicates in larger codebases?
What risk exists if a type predicate's runtime logic doesn't actually match its declared type guarantee?
Have you used Zod or a similar library to validate unknown data before?

Common Mistakes
❌ Reaching for a direct type assertion on unknown data instead of writing or using a proper runtime check.
❌ Writing a type predicate whose actual runtime logic doesn't fully guarantee what it claims to guarantee, creating a false sense of safety.

Interview Tips
Interview Tip:
Bring up Zod again here explicitly, since this question sets up perfectly for the dedicated runtime validation topic if it comes up later in the interview.

TOPIC 37 - CONTROL FLOW NARROWING & TYPE GUARDS
====================================================

Question 1
What is control flow analysis in TypeScript, and how does it enable type narrowing?

Answer
Control flow analysis is the mechanism TypeScript uses to track how a variable's possible type changes as execution flows through different branches, conditions, loops, and early returns in your code. Every time you perform a check, like typeof, instanceof, a truthiness check, or an equality comparison, TypeScript updates its understanding of that variable's type for the remainder of that specific code path. This is what allows narrowing to work seamlessly without any extra syntax, the compiler is essentially simulating how the code would actually execute and refining types accordingly at every branch point.

Example
function process(value: string | number | null) {
  if (value === null) {
    return; // early return narrows value to string | number for the rest of the function
  }
  if (typeof value === "string") {
    console.log(value.toUpperCase()); // narrowed to string
    return;
  }
  console.log(value.toFixed(2)); // narrowed to number by elimination
}

Follow-up Questions
Does control flow narrowing persist across function boundaries or closures?
How does an early return affect narrowing for the rest of the function body?
What happens to narrowing when a variable is reassigned partway through a function?

Common Mistakes
❌ Assuming narrowing automatically persists inside a callback or a separate function defined within the same scope.
❌ Not leveraging early returns to simplify narrowing logic, leading to deeply nested conditionals instead.

Interview Tips
Interview Tip:
Mention that narrowing can be lost when crossing into a nested function or callback, since TypeScript can't guarantee the outer variable wasn't reassigned by the time that callback actually runs, this is a genuinely important caveat.

----------------------------------------------------

Question 2
What is a custom type guard, and how do you write one using a type predicate?

Answer
A custom type guard is a function that performs some runtime check and tells TypeScript, through its return type, that the check guarantees the input is a specific, narrower type when the function returns true. You write this using a type predicate, syntax of the form "parameterName is SomeType" as the function's return type, instead of a plain boolean. Once you use this function inside a conditional, TypeScript trusts its declared guarantee and narrows the checked value accordingly within that branch, exactly the same as it would with a built-in check like typeof.

Example
interface Fish { swim(): void; }
interface Bird { fly(): void; }

function isFish(animal: Fish | Bird): animal is Fish {
  return (animal as Fish).swim !== undefined;
}

function move(animal: Fish | Bird) {
  if (isFish(animal)) {
    animal.swim(); // narrowed to Fish
  } else {
    animal.fly(); // narrowed to Bird
  }
}

Follow-up Questions
What happens if a type predicate's actual logic doesn't correctly match what it claims?
How is a type predicate different from just returning a plain boolean?
Can type predicates be used with array filter for narrowing an entire array?

Common Mistakes
❌ Writing a type predicate whose runtime check doesn't actually guarantee the claimed type, creating an unsafe, false guarantee.
❌ Forgetting the special "parameterName is Type" syntax and just returning a plain boolean instead, which provides no narrowing benefit at all.

Interview Tips
Interview Tip:
Point out explicitly that TypeScript trusts a type predicate's claim completely without verifying it, so it's entirely on the developer to make sure the logic is actually correct, this is a subtle but important responsibility.

----------------------------------------------------

Question 3
How does TypeScript narrow types inside a switch statement, and how does this connect to exhaustiveness checking?

Answer
A switch statement narrows a discriminated union in essentially the same way an if/else chain does, checking a discriminant property's value against each case, and narrowing the type within each case block accordingly. What makes switch statements especially powerful for discriminated unions is combining them with an exhaustiveness check in the default case, assigning the still-unhandled value to a variable explicitly typed as never; if every case has genuinely been handled, that assignment is valid, but if a new union member is added later and a case is missing, the compiler immediately flags that the value isn't actually never at that unhandled point, forcing you to catch the omission at compile time rather than at runtime.

Example
type Action = { type: "increment" } | { type: "decrement" } | { type: "reset"; value: number };

function reducer(state: number, action: Action): number {
  switch (action.type) {
    case "increment": return state + 1;
    case "decrement": return state - 1;
    case "reset": return action.value;
    default:
      const exhaustiveCheck: never = action;
      return exhaustiveCheck;
  }
}

Follow-up Questions
What error would you see if a new Action variant were added but not handled in the switch?
Why is exhaustiveness checking especially valuable in something like a reducer function?
Does this pattern require the "strict" compiler flag to work correctly?

Common Mistakes
❌ Skipping the default-case exhaustiveness check entirely, silently allowing unhandled union members to slip through.
❌ Not connecting this pattern to real-world reducer functions, like those in Redux or useReducer.

Interview Tips
Interview Tip:
Tie this directly to a Redux-style or useReducer-style reducer function, it's an extremely relatable, real-world scenario that most frontend interviewers will immediately recognize and appreciate.

TOPIC 38 - ASYNC/AWAIT & PROMISES
====================================================

Question 1
How does TypeScript type a Promise, and what role does the generic type parameter play?

Answer
A Promise is a generic type, Promise<T>, where T represents the type of the value the promise will eventually resolve to. When you write an async function, TypeScript automatically infers or requires that return type to be wrapped in Promise, based on whatever value the function body actually returns. This generic parameter is what allows tools and other code to know, at compile time, exactly what type of data will be available once the promise resolves, without needing to actually run the asynchronous operation first.

Example
function delay(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

function fetchScore(): Promise<number> {
  return new Promise((resolve) => resolve(95));
}

async function main() {
  await delay(1000);
  const score: number = await fetchScore(); // T is unwrapped automatically by await
}

Common Mistakes

❌ Not understanding that await unwraps exactly one level of Promise, matching what Awaited does at the type level.

Interview Tips
Interview Tip:
Explicitly connect await's behavior to the Awaited utility type discussed earlier, showing that these topics are two views of the exact same underlying mechanism reinforces a cohesive understanding.

Question 2
How should you type and handle errors thrown inside an async function using try/catch?

Answer
JavaScript allows throwing any value at all, not just Error instances, which means the catch clause's parameter is typed as unknown by default under strict settings, rather than automatically being typed as Error. This forces you to properly narrow the caught value before accessing anything on it, typically with an instanceof Error check, since blindly assuming every caught value has a message property would be unsafe and inaccurate.

Example
async function fetchData(url: string): Promise<string> {
  try {
    const response = await fetch(url);
    if (!response.ok) {
      throw new Error(`Request failed with status ${response.status}`);
    }
    return await response.text();
  } catch (error) {
    if (error instanceof Error) {
      console.error("Fetch failed:", error.message);
    } else {
      console.error("Unknown error:", error);
    }
    throw error;
  }
}

Interview Tips

Question 3
What is the difference between running multiple async operations sequentially with multiple await statements versus concurrently with Promise.all?

Answer
Writing multiple await statements one after another runs each asynchronous operation sequentially, the second one doesn't even start until the first one has fully completed, which is correct when operations genuinely depend on each other's results, but wastes time when they're actually independent. Using Promise.all instead starts every operation immediately and concurrently, then waits for all of them to finish together, which is significantly faster whenever the operations don't depend on each other. From a typing perspective, both approaches are fully type-safe, the real difference is purely about runtime performance and correctly modeling actual dependencies between operations.

Example
// Sequential: slower, appropriate only if postsData actually depends on userData
async function loadSequential() {
  const userData = await fetchUser();
  const postsData = await fetchPosts();
  return { userData, postsData };
}

// Concurrent: faster, correct when the two calls are fully independent
async function loadConcurrent() {
  const [userData, postsData] = await Promise.all([fetchUser(), fetchPosts()]);
  return { userData, postsData };
}

async function fetchUser() { return { name: "Afnan" }; }
async function fetchPosts() { return [{ title: "Post 1" }]; }

Follow-up Questions
When would sequential awaits actually be the correct, necessary choice?
How does Promise.all handle one of several promises rejecting?
What would you use if you wanted all results regardless of individual failures?

Common Mistakes
❌ Defaulting to sequential awaits out of habit even when the operations are genuinely independent and could run concurrently.
❌ Forgetting that Promise.all rejects immediately if even one input promise rejects, potentially losing results from the others that did succeed.

Interview Tips
Interview Tip:
If asked about partial failure handling, mention Promise.allSettled as the correct tool when you need every result regardless of individual success or failure, this shows awareness of the full Promise API, not just the basics.

TOPIC 39 - TYPE PREDICATES
====================================================

Question 1
What exactly is a type predicate, and what does the "is" keyword mean in a function's return type?

Answer
A type predicate is a special return type annotation used specifically on functions meant to act as type guards. It's written as "parameterName is SomeType" instead of a normal type, and it tells the compiler: whenever this function returns true, treat the given parameter as narrowed to SomeType for the rest of that code path. The "is" keyword itself doesn't perform any check on its own, the actual runtime logic inside the function body is entirely up to you, "is" is purely a signal to the type checker about what a true result should mean.

Example
function isString(value: unknown): value is string {
  return typeof value === "string";
}

function processValue(value: unknown) {
  if (isString(value)) {
    console.log(value.length); // narrowed to string
  }
}

Follow-up Questions

What would happen if you used a plain boolean return type instead of a type predicate here?

Common Mistakes
❌ Believing TypeScript verifies the correctness of a type predicate's underlying logic, it doesn't, the developer is fully responsible for accuracy.
❌ Forgetting the "is" keyword entirely and just declaring a boolean return type, which loses all narrowing behavior.

Interview Tips
Interview Tip:
Reiterate clearly that the compiler trusts type predicates completely without verification, incorrect predicates are a real, self-inflicted source of bugs, and acknowledging that risk shows mature understanding.

Question 2
How would you write a type predicate to filter an array and get a properly narrowed, more specific array type back?

Answer
Array.prototype.filter is specially typed to recognize when its callback is a type predicate, and when it is, the resulting array's type is narrowed accordingly, rather than staying as the original, broader element type. This is one of the most practical, everyday applications of type predicates, commonly used to strip out null or undefined values, or to separate a union array into its more specific constituent types.

Example
interface Task { id: string; completed: boolean; assignee?: string; }

function hasAssignee(task: Task): task is Task & { assignee: string } {
  return task.assignee !== undefined;
}

const tasks: Task[] = [
  { id: "1", completed: false, assignee: "Afnan" },
  { id: "2", completed: true },
];

const assignedTasks = tasks.filter(hasAssignee); // Array<Task & { assignee: string }>

Question 3
What is an "assertion function," and how is it different from a regular type predicate?

Answer
An assertion function is closely related to a type predicate but uses different syntax, "asserts parameterName is SomeType," and instead of returning a boolean that you then check in an if statement, it either throws an error or returns normally, and if it returns normally without throwing, TypeScript treats everything after that call as narrowed for the rest of the function, without needing an explicit if block at all. This mirrors patterns like Node's assert function, or custom validation helpers meant to be called once at the top of a function to guarantee an input's shape before proceeding.

Example
function assertIsString(value: unknown): asserts value is string {
  if (typeof value !== "string") {
    throw new Error("Expected a string");
  }
}

function processInput(value: unknown) {
  assertIsString(value);
  console.log(value.toUpperCase()); // narrowed to string immediately after the assertion call, no if needed
}

Follow-up Questions
Why doesn't an assertion function need to be wrapped in an if statement to achieve narrowing?
What happens to the narrowing if the assertion function is called conditionally, only inside some branches?
How does this pattern compare to Node's built-in assert module?

Common Mistakes
❌ Wrapping an assertion function call in an unnecessary if check, when the whole point is that it narrows unconditionally after the call.
❌ Forgetting an assertion function must actually throw for its narrowing guarantee to hold true at runtime.

Interview Tips
Interview Tip:
Point out that assertion functions are ideal for guard-clause-style validation at the top of a function, since they narrow the rest of the function body without adding extra indentation or nested if blocks.

TOPIC 40 - RUNTIME VALIDATION (ZOD)
====================================================

Question 1
Why is runtime validation still necessary even in a fully typed TypeScript codebase?

Answer
TypeScript's types only exist at compile time and are completely erased before the code actually runs, which means they provide zero protection against data that enters your application from outside its control, things like API responses, user input, form submissions, environment variables, or query parameters. If you type an API response as a specific interface without verifying the actual data matches, you're just trusting the data blindly, and any mismatch will cause a runtime error somewhere downstream, often far from where the actual bad data first entered the system, making it hard to trace. Runtime validation closes exactly this gap, actually checking that incoming data matches your expectations before you treat it as trustworthy.

Example
interface User { id: string; email: string; }

async function getUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${id}`);
  return response.json(); // TypeScript trusts this completely, with zero actual verification
}
// If the API changes shape, this compiles fine but crashes unpredictably later in the app

Follow-up Questions
Where in an application's data flow is runtime validation most critical?
What's the risk of trusting an untyped JSON response without validation?
How does this connect back to the difference between unknown and a type assertion?

Common Mistakes
❌ Believing a TypeScript interface itself provides any actual runtime guarantee about external data.
❌ Skipping validation at trust boundaries, like API responses or form inputs, where bad data most commonly enters an application.

Interview Tips
Interview Tip:
Use the phrase "trust boundary" when describing where validation belongs, at the edges of your application where you don't control the incoming data, that's precise, professional terminology that resonates in interviews.

----------------------------------------------------

Question 2
How does Zod work, and how does it let you derive a TypeScript type directly from a runtime schema?

Answer
Zod is a schema declaration and validation library where you define a schema describing the expected shape of your data using its own composable API, and that schema is both a real, runtime-checkable object and the single source of truth for the corresponding TypeScript type. Using Zod's "infer" utility, you can derive a fully accurate TypeScript type directly from the schema, meaning your runtime validation logic and your compile-time type definition can never drift apart, since one is generated directly from the other rather than maintained as two separate, easily desynced definitions.

Example
import { z } from "zod";

const UserSchema = z.object({
  id: z.string(),
  email: z.string().email(),
  age: z.number().min(0).optional(),
});

type User = z.infer<typeof UserSchema>; // { id: string; email: string; age?: number }

async function getUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${id}`);
  const data = await response.json();
  return UserSchema.parse(data); // throws at runtime if the shape doesn't actually match
}

Follow-up Questions
What is the difference between Zod's parse method and its safeParse method?
Why is deriving the type from the schema better than maintaining a separate interface alongside it?
How would you handle a validation failure gracefully instead of letting parse throw?

Common Mistakes
❌ Manually maintaining a separate TypeScript interface alongside a Zod schema instead of deriving it with z.infer.
❌ Using parse everywhere without considering safeParse for cases where you want to handle failures gracefully instead of catching a thrown error.

Interview Tips
Interview Tip:
Explain z.infer as "generating your TypeScript type from your validation logic instead of the other way around," this framing captures exactly why Zod is considered such a strong pairing with TypeScript.

----------------------------------------------------

Question 3
What is the difference between Zod's parse and safeParse methods, and when would you use each?

Answer
parse validates the input against the schema and, if successful, returns the correctly typed, validated data directly; if validation fails, it throws an exception containing detailed information about what went wrong. safeParse does the same validation, but instead of throwing, it returns a result object with a success flag, letting you handle both the success and failure cases explicitly through normal control flow rather than a try/catch block. I use parse when a validation failure represents a genuinely exceptional, unrecoverable situation I want to propagate as an error, and safeParse when I want to gracefully handle invalid input, for example showing field-specific validation errors on a form.

Example
import { z } from "zod";

const LoginSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
});

function validateLogin(input: unknown) {
  const result = LoginSchema.safeParse(input);
  if (!result.success) {
    return { errors: result.error.flatten().fieldErrors };
  }
  return { data: result.data }; // fully typed as { email: string; password: string }
}

Follow-up Questions
Why would a form validation scenario prefer safeParse over parse?
How would you extract user-friendly error messages from a failed safeParse result?
Does safeParse have any performance advantage over parse when validation is expected to fail often?

Common Mistakes
❌ Using parse in a context, like form validation, where failure is an expected, routine outcome rather than an exceptional one.
❌ Not knowing how to access and format the detailed error information from a failed safeParse result.

Interview Tips
Interview Tip:
Tie your answer to a form-validation scenario specifically, it's the most relatable, common real-world case for choosing safeParse over parse and shows practical, everyday familiarity with the library.

TOPIC 41 - CONSTRUCTOR PARAMETER PROPERTIES (ADVANCED)
====================================================

Question 1
Can constructor parameter properties be combined with readonly, and what does that guarantee?

Answer
Yes, readonly can be combined with any of the access modifiers, public, private, or protected, directly in the constructor parameter list, which both declares the property, assigns it from the constructor argument, and locks it from ever being reassigned after that initial assignment, all in a single, compact declaration. This combination is extremely common for entity identifiers or other values that should genuinely never change after an object is created, since it communicates that immutability guarantee directly and concisely right in the constructor signature, rather than needing a separate property declaration line.

Example
class Order {
  constructor(
    public readonly orderId: string,
    private readonly createdAt: Date = new Date(),
    public status: "pending" | "shipped" = "pending"
  ) {}
}

const order = new Order("ORD-123");
order.orderId = "ORD-456"; // error: cannot assign to 'orderId' because it is a read-only property
order.status = "shipped"; // valid, status wasn't marked readonly

Follow-up Questions
Why is readonly particularly common on identifier-like properties such as an order ID or user ID?
Does readonly here still only offer compile-time protection, consistent with how readonly behaves everywhere else?
Can you mix readonly parameter properties with regular, non-property constructor parameters in the same constructor?

Common Mistakes
❌ Forgetting readonly parameter properties still only enforce immutability at compile time, not genuinely at runtime.
❌ Not realizing you can freely mix parameter properties with plain, non-property constructor parameters in the same parameter list.

Interview Tips
Interview Tip:
Reinforce the compile-time-only nature of readonly here too, it's the same underlying limitation discussed with private and readonly elsewhere, and connecting these dots shows a consistent, well-integrated mental model.

----------------------------------------------------

Question 2
What happens if you mix parameter properties with regular constructor logic that references "this" before all properties are assigned?

Answer
Parameter properties are assigned automatically at the very start of the constructor's execution, effectively before any of your own explicit constructor body code runs, similar to how JavaScript's own class field initialization order works. This means it's generally safe to reference "this.propertyName" for a parameter property anywhere within the constructor body, since it will have already been assigned by the time your own code executes, but you do need to be careful about the relative order between parameter properties and any regular class fields declared with initializers outside the constructor, since JavaScript's actual initialization order can be a source of subtle bugs if you're not paying attention to it.

Example
class Logger {
  private prefix: string = "[LOG]"; // class field, initialized before constructor body runs

  constructor(private context: string) {
    console.log(`${this.prefix} ${this.context}`); // both are safely available here
  }
}

new Logger("AuthService"); // "[LOG] AuthService"

Follow-up Questions
What is the actual initialization order between class field initializers and constructor parameter properties?
Could this ordering behavior cause a bug if a class field initializer depended on a constructor parameter property?
Have you run into an initialization-order bug like this in a real codebase?

Common Mistakes
❌ Assuming class field initializers and constructor logic run in an arbitrary or unpredictable order, the actual order is well-defined and worth knowing precisely.
❌ Writing a class field initializer that depends on a constructor parameter property, which can fail depending on the exact ordering involved.

Interview Tips
Interview Tip:
If you're not 100 percent certain of the exact initialization order in a specific edge case, it's fine to say you'd verify it rather than guessing confidently, that honesty is better than confidently stating something incorrect.

TOPIC 42 - ENUMS & ABSTRACT CLASSES
====================================================

Question 1
What is an enum in TypeScript, and what problem does it solve?

Answer
An enum defines a set of named constants, giving meaningful names to a fixed collection of related values instead of scattering magic strings or numbers throughout your code. Numeric enums, by default, auto-assign incrementing numbers starting from zero, while string enums require you to explicitly assign a string value to each member. Enums exist at runtime, unlike interfaces or type aliases, they actually generate real JavaScript code, typically an object, that you can inspect and iterate over, which is a meaningful difference from purely compile-time constructs.

Example
enum OrderStatus {
  Pending,
  Shipped,
  Delivered,
  Cancelled,
}

enum Direction {
  Up = "UP",
  Down = "DOWN",
  Left = "LEFT",
  Right = "RIGHT",
}

function move(direction: Direction) {
  console.log(`Moving ${direction}`);
}

move(Direction.Up);

Follow-up Questions
Do enums exist in the compiled JavaScript, or do they get erased like interfaces?
What's the difference between a numeric enum and a string enum?
Why might a team choose a union of string literals over an enum?

Common Mistakes
❌ Assuming enums are completely erased at compile time the same way interfaces and type aliases are.
❌ Not knowing string enums require an explicit value for every member, unlike numeric enums.

Interview Tips
Interview Tip:
Explicitly state that enums generate real runtime JavaScript code, this is one of the most important, frequently tested facts distinguishing enums from nearly every other TypeScript-only construct.

----------------------------------------------------

Question 2
What are the downsides of TypeScript enums, and why do some teams prefer union types of string literals instead?

Answer
Regular enums generate actual JavaScript code that adds to your bundle size, and numeric enums specifically create a confusing, bidirectional mapping, both from name to number and number back to name, which can be surprising and isn't always useful. Enums also don't interoperate perfectly with plain JavaScript or JSON data the way you might expect, comparing a numeric enum value directly to a raw number from an API works, but it's not always obvious it will. A union of string literals, by contrast, is completely erased at compile time, adds zero runtime overhead, works naturally with plain string data from APIs, and is generally considered by many in the TypeScript community, including some official guidance, to be the more modern, lightweight choice for representing a fixed set of options.

Example
// Enum approach: generates runtime code, adds bundle size
enum Status { Active, Inactive }

// Union of literals approach: erased completely, zero runtime cost
type StatusLiteral = "active" | "inactive";

function setStatus(status: StatusLiteral) { /* ... */ }
setStatus("active"); // works naturally with plain strings from an API, no enum member needed

Follow-up Questions
What is the confusing bidirectional mapping behavior specific to numeric enums?
What is a "const enum," and does it solve the bundle-size concern?
Which would you personally default to on a new project, and why?

Common Mistakes
❌ Not being aware of the reverse-mapping behavior unique to numeric enums, which can be a genuine source of confusion.
❌ Presenting enums as having no real downsides at all, when this is actually a well-known, actively debated trade-off in the community.

Interview Tips
Interview Tip:
Having a clear, personal default preference here, and being able to justify it with the bundle-size and interoperability points, demonstrates real, considered opinions rather than just reciting both sides neutrally.

----------------------------------------------------

Question 3
What is a "const enum," and how is it different from a regular enum?

Answer
A const enum is declared the same way as a regular enum but with the const keyword in front, and it tells the compiler to fully inline every usage of the enum's members directly at their call sites during compilation, rather than generating an actual runtime object that gets referenced. This eliminates the runtime code and bundle-size overhead of a regular enum entirely, while still letting you use the same enum syntax in your source code. The trade-off is that const enums can't be used with certain build tools that only transpile one file at a time without full type information, since inlining requires knowing the enum's values at compile time across files, which is also exactly why isolatedModules often disallows const enums outright.

Example
const enum Direction {
  Up,
  Down,
}

function move(direction: Direction) {
  console.log(direction);
}

move(Direction.Up); // compiles down to move(0), fully inlined, no Direction object exists at runtime

Follow-up Questions
Why do const enums cause issues with single-file transpilers like Babel or esbuild?
How does isolatedModules relate to the restriction on const enums?
Would you recommend const enums for a library meant to be consumed by many different build setups?

Common Mistakes
❌ Assuming const enums behave identically to regular enums with just a minor performance tweak, the difference in generated output is actually fundamental.
❌ Using const enums in a library published for public consumption without considering downstream build tool compatibility.

Interview Tips
Interview Tip:
Mention the isolatedModules incompatibility specifically, it's a very concrete, practical reason const enums are often avoided in modern projects that rely on tools like esbuild, swc, or Babel for transpilation.

----------------------------------------------------

Question 4
What is an abstract class, and how is it different from a regular class or an interface?

Answer
An abstract class is a class that cannot be instantiated directly, it exists specifically to be extended by subclasses, and it can define both fully implemented methods that subclasses inherit as-is, and abstract methods, which have no implementation in the base class and must be implemented by every concrete subclass that extends it. This sits conceptually between a plain interface, which defines a shape with zero implementation at all, and a regular class, which provides a complete, directly instantiable implementation. Abstract classes are the right tool when you want to share some common, concrete implementation across subclasses while still enforcing that certain specific methods must be individually implemented by each one.

Example
abstract class Shape {
  abstract area(): number; // no implementation, subclasses must provide one

  describe(): string { // concrete, shared implementation
    return `This shape has an area of ${this.area()}`;
  }
}

class Circle extends Shape {
  constructor(private radius: number) { super(); }
  area(): number {
    return Math.PI * this.radius ** 2;
  }
}

const shape = new Shape(); // error: cannot create an instance of an abstract class
const circle = new Circle(5); // valid

Follow-up Questions
Why can't an abstract class be instantiated directly?
How is an abstract class different from an interface in terms of code sharing?
Can an abstract class have a constructor, and can subclasses call it with super()?

Common Mistakes
❌ Trying to instantiate an abstract class directly, then being confused by the resulting compile error.
❌ Not recognizing when an abstract class is more appropriate than an interface, specifically when there's genuine shared implementation to provide.

Interview Tips
Interview Tip:
Summarize the choice clearly: interfaces for pure shape with zero implementation, abstract classes for shared implementation plus a partial, enforced contract, regular classes for a fully complete, directly usable implementation. This three-way framing answers a lot of related follow-ups at once.

TOPIC 43 - MAPPED TYPES & CONDITIONAL TYPES
====================================================

Question 1
What is a mapped type, and how does the "in" keyword work inside one?

Answer
A mapped type builds a new object type by iterating over the keys of an existing type, using syntax that looks similar to a for...in loop but operates entirely at the type level. The "in" keyword iterates over a union of keys, typically produced by keyof on another type, and for each key, you define what the resulting property's type should be, often by referencing the original property's type through an indexed access. This is exactly the mechanism behind built-in utility types like Partial, Required, and Readonly, they're not special compiler magic, they're just mapped types someone already wrote for you.

Example
type MyReadonly<T> = {
  readonly [P in keyof T]: T[P];
};

interface Point { x: number; y: number; }
type ReadonlyPoint = MyReadonly<Point>; // { readonly x: number; readonly y: number }

Follow-up Questions
How does a mapped type differ from manually writing out each property one by one?
Can a mapped type add or remove modifiers like readonly and optional at the same time?
How would you write a mapped type that transforms every property's value type, not just its modifiers?

Common Mistakes
❌ Assuming mapped types are a distinct compiler feature separate from utility types, rather than the underlying mechanism utility types are built with.
❌ Forgetting that keyof is almost always the source of the key union being iterated over.

Interview Tips
Interview Tip:
Emphasize that literally every basic object utility type, Partial, Required, Readonly, Pick, is just a mapped type someone wrote once, this framing shows you understand the type system's actual building blocks, not just memorized utility names.

----------------------------------------------------

Question 2
How do you use mapped type modifiers to add or remove "readonly" and "optional" from properties?

Answer
Mapped types support explicit plus and minus prefixes on the readonly and optional modifiers, letting you not just add them, which is the default behavior when you write them plainly, but explicitly remove them too, using a minus sign. This is exactly how the Required utility type works, it uses -? to strip optionality from every property, forcing them all to be mandatory, and it's how a "mutable" counterpart to Readonly can be built, using -readonly to strip immutability back off.

Example
type MyRequired<T> = {
  [P in keyof T]-?: T[P]; // minus removes the optional modifier
};

type Mutable<T> = {
  -readonly [P in keyof T]: T[P]; // minus removes the readonly modifier
};

interface Config { debug?: boolean; readonly version: string; }
type FullConfig = MyRequired<Config>; // { debug: boolean; version: string }
type MutableConfig = Mutable<Config>; // { debug?: boolean; version: string }

Follow-up Questions
What does a plain, unprefixed readonly or optional modifier do by default in a mapped type?
Why doesn't TypeScript ship a built-in "Mutable" utility type the way it ships Readonly?
Could you combine both -readonly and -? in the same mapped type?

Common Mistakes
❌ Not knowing the -? and -readonly syntax exists at all, assuming mapped types can only add modifiers, never remove them.
❌ Forgetting these modifier prefixes can be combined together within a single mapped type definition.

Interview Tips
Interview Tip:
Writing MyRequired and Mutable from memory, side by side, is a great way to demonstrate real command over mapped type modifiers rather than surface-level familiarity with just Partial and Readonly.

----------------------------------------------------

Question 3
What is key remapping in mapped types, and what does the "as" clause do?

Answer
Key remapping, introduced through an "as" clause directly inside a mapped type's key position, lets you transform the actual key names themselves during the mapping process, not just their associated value types. This is commonly combined with template literal types to programmatically generate new property names based on the original ones, for example turning every property "foo" into "getFoo", which is exactly the mechanism behind auto-generating typed getter method signatures from a plain data shape.

Example
type Getters<T> = {
  [P in keyof T as `get${Capitalize<string & P>}`]: () => T[P];
};

interface Person { name: string; age: number; }
type PersonGetters = Getters<Person>;
// { getName: () => string; getAge: () => number }

Follow-up Questions
How does the "as" clause combine with template literal types to build new key names?
Can key remapping be used to filter out certain properties entirely, not just rename them?
Where might auto-generated getter or setter types like this be useful in a real project?

Common Mistakes
❌ Not knowing the "as" clause exists, and assuming mapped types can only reuse the original key names unchanged.
❌ Forgetting that mapping a key to "never" inside the "as" clause is the technique used to filter properties out entirely.

Interview Tips
Interview Tip:
Mention that mapping a key to never inside the as clause is exactly how you'd filter out unwanted properties in a mapped type, this is a genuinely advanced trick that very few candidates know, and bringing it up unprompted stands out.

----------------------------------------------------

Question 4
What is a conditional type, and how does the syntax work?

Answer
A conditional type selects between two possible types based on a type-level condition, written with syntax that mirrors a JavaScript ternary expression: "T extends U ? TrueType : FalseType". If T is assignable to U, the conditional resolves to TrueType, otherwise it resolves to FalseType. This is the foundational building block behind many built-in utility types, like Exclude, Extract, and NonNullable, and it lets you write types whose actual shape depends on some other type, enabling genuinely dynamic, reusable type-level logic rather than static, fixed type definitions.

Example
type IsString<T> = T extends string ? "yes" : "no";

type A = IsString<string>; // "yes"
type B = IsString<number>; // "no"

type ElementType<T> = T extends (infer U)[] ? U : T;
type NumberArrayElement = ElementType<number[]>; // number
type NotAnArray = ElementType<boolean>; // boolean, falls through to the false branch

Follow-up Questions
How is a conditional type similar to a ternary expression in regular JavaScript?
What does "distributive" mean in the context of conditional types over a union?
How does the infer keyword work within a conditional type?

Common Mistakes
❌ Confusing conditional type syntax with a runtime ternary expression, they look similar but operate on entirely different things, types versus values.
❌ Not being able to explain what happens when the checked type T is itself a union.

Interview Tips
Interview Tip:
Draw the direct parallel to a JavaScript ternary explicitly, "just like value ? a : b, but for types instead of values," this analogy makes the syntax immediately click for anyone hearing it explained this way.

----------------------------------------------------

Question 5
What does the "infer" keyword do inside a conditional type, and why is it so useful?

Answer
infer lets you introduce a new, anonymous type variable directly within the extends clause of a conditional type, and TypeScript automatically infers what that variable should be based on the actual structure being matched against. This is incredibly useful for extracting a specific piece out of a larger, more complex type, like pulling the element type out of an array, the resolved type out of a Promise, or a specific parameter type out of a function signature, all without needing to know the exact concrete type ahead of time, since infer lets the compiler figure it out dynamically based on whatever type is actually passed in.

Example
type UnwrapPromise<T> = T extends Promise<infer U> ? U : T;

type A = UnwrapPromise<Promise<string>>; // string
type B = UnwrapPromise<number>; // number, not a Promise, so it passes through unchanged

type FirstParameter<T> = T extends (first: infer P, ...rest: any[]) => any ? P : never;
type P1 = FirstParameter<(name: string, age: number) => void>; // string

Follow-up Questions
How is infer actually used internally to implement the built-in ReturnType utility type?
Can you use infer more than once within the same conditional type?
What happens if the structure being matched doesn't actually contain the pattern you're trying to infer from?

Common Mistakes
❌ Assuming infer requires knowing the concrete type ahead of time, when its entire purpose is inferring an unknown piece dynamically.
❌ Not being able to explain how ReturnType itself is implemented using exactly this pattern.

Interview Tips
Interview Tip:
Show the actual, real implementation of ReturnType, "T extends (...args: any[]) => infer R ? R : any", connecting a genuinely advanced concept back to a utility type the interviewer almost certainly already uses daily is a very strong close to this topic.

----------------------------------------------------

Question 6
What is a distributive conditional type, and how does it behave differently when the checked type is a union versus a single type?

Answer
When a conditional type's checked type, the thing directly before "extends", is a bare, naked generic type parameter, and you pass in a union as that type argument, TypeScript automatically distributes the conditional across every member of the union individually, applying the condition to each one separately and then combining the results back into a new union, rather than treating the whole union as one single value being checked all at once. This distributive behavior is exactly what powers Exclude and Extract. If you don't want this automatic distribution, you can suppress it by wrapping both the checked type and the comparison type in tuples, like [T] extends [U], which forces the union to be treated as one single, non-distributed value.

Example
type ToArray<T> = T extends any ? T[] : never;

type Result = ToArray<string | number>; // string[] | number[], distributed across the union

type ToArrayNonDist<T> = [T] extends [any] ? T[] : never;
type ResultNonDist = ToArrayNonDist<string | number>; // (string | number)[], NOT distributed

Follow-up Questions
Why does wrapping T and U in tuples suppress the distributive behavior?
Can you think of a real scenario where you'd deliberately want to disable distribution?
How does this distributive behavior explain how Exclude actually removes members from a union?

Common Mistakes
❌ Being surprised that a conditional type applied to a union produces a new union instead of a single combined result.
❌ Not knowing the tuple-wrapping trick for disabling distribution when it's genuinely not the desired behavior.

Interview Tips
Interview Tip:
This is consistently one of the most advanced, most discriminating TypeScript interview questions at the senior level. Being able to explain both the default distributive behavior and the tuple trick to disable it, from memory, is a genuinely strong signal of deep expertise.
